## 一、核心功能模块梳理与成熟度评估

### 1.1 架构与模块关系

```
前端层   haoyue_cli（终端渲染）   haoyue_desktop（Electron+Vue3）
              │ CLI 直连               │ JSON-RPC
              └────────► haoyue_runtime ◄──────── haoyue_webserver（官网/技能市场，独立部署）
                          │
   ┌──────────┬───────────┼───────────┬──────────────┐
 Agents 主循环  Providers 三客户端   Daemon(60+ RPC)  Data(SQLite)
 Tools(12内置+MCP动态)  Mcp(stdio/SSE)  Skills  Scheduling  Sessions
 ComputerUse(4平台驱动)  Experts  Prompts(热加载)  Verification  Workspaces
```

- **数据流**：前端 → Daemon（Named Pipe / Unix Socket）→ Agent 主循环 → ProviderManager（路由/重试/熔断）→ LLM；工具调用经 ToolRegistry → 内置工具 / MCP 动态工具。
- **持久化**：统一 SQLite（`haoyue.db`：会话、项目列表、定时任务、知识库）；配置仍为 JSON 文件（`~/.haoyue/config.json`）。
- **扩展轴**：Tools / Skills / Prompts / MCP 四层（`Extensions/` 机制目前仅承载 ComputerUse 一个扩展）。

## 二、缺失功能识别与优先级排序

排序依据：**用户价值（目标用户群的受益面）× 实现成本（基于现有代码的可复用度）**，高优先级 = 高价值且低成本，或战略必需。

### 高优先级

| # | 缺失功能 | 依据 | 价值 / 成本 |
|---|---|---|---|
| H1 | **自定义专家（CRUD）** | `ExpertCatalog.cs` 代码注释明言后续支持；`expert.list` 线格式已稳定（record 含 7 字段），只需加存储表 + `expert.upsert/remove` RPC + 桌面端编辑器 | 个性化是 Agent 产品核心场景；静态目录 8 个专家无法覆盖垂直需求 / 成本低-中（数据结构现成） |
| H2 | **会话内容搜索** | Daemon 白名单有 session.list/get/fork 等 7 方法，无搜索；会话已在 SQLite（`Sessions/`），加 `session.search` 即可 | 「上次讨论过 X」是高频找回场景，现只能逐条翻 / 成本低（LIKE 或 FTS5） |
| H3 | **工具级权限控制** | `AgentMode.cs` 仅 plan/edit 两级；工具接口有 `Mutating` 标记但无逐工具审批流、无 allowlist 配置 | bash/edit_file 是高权操作，企业/新用户需要信任门槛 / 成本中（需 UI 审批回路） |
| H4 | **知识库导出/备份** | Daemon 有 knowledge.import/list/save/search/delete，无 export；知识是用户长期资产，换机/迁移无路径 | 数据可携带性是信任基础 / 成本低（JSON/Markdown 导出即可） |

### 中优先级

| # | 缺失功能 | 依据 | 价值 / 成本 |
|---|---|---|---|
| M1 | **子 Agent / 任务委派** | 工具全量清单无 spawn/task/subagent 类工具；复杂多步任务只能单循环跑（MaxSteps=40 封顶） | 大幅提升复杂任务成功率 / 成本高（上下文隔离、结果聚合、并发控制） |
| M2 | **MCP resources/prompt 注入上下文** | `McpClient.cs` 已发现三类能力，但 `PromptProvider` 槽位仅四类，未见 resources 内容注入提示链路 | 补全 MCP 协议价值 / 成本中 |
| M3 | **Embedding 客户端与语义检索** | `ModelCapabilities.Embedding` 字段已存在（HaoyueConfig.cs），但 `ILlmClient` / `ProviderManager` 无 embedding 方法 | 知识检索从词面匹配升级语义匹配 / 成本中 |
| M4 | **技能 manifest 增强** | `SkillManifest` 仅 4 字段；无 allowed-tools（技能权限）、无参数化、无触发条件 | 技能安全性 + 表达力；是技能生态繁荣的前提 / 成本中 |
| M5 | **定时任务失败通知** | `ScheduleRunStatus` 记录状态，但无通知通道（桌面通知/邮件/webhook）；失败任务静默 | 定时任务的可靠性闭环 / 成本中 |
| M6 | **CLI 管理命令补齐** | CLI 仅 provider/model/mcp/skill/sessions/doctor 六组（Commands/ 共 857 行）；knowledge/rules/memory/expert/schedule 仅桌面端可用 | 服务器/SSH 场景用户功能不完整 / 成本低-中（daemon RPC 全部现成，纯 CLI 壳） |
| M7 | **Mac 驱动功能补齐** | MacDriver 134 行 vs WindowsDriver 1328 行（同为四接口实现，深度差一个量级） | macOS 体验对齐 / 成本中 |

### 低优先级

| # | 缺失功能 | 依据 | 说明 |
|---|---|---|---|
| L1 | 自动更新通道 | `RELEASING.md` 手动分步流程；无 electron-updater | 发布效率问题，非用户功能 |
| L2 | 桌面 UI i18n | 界面文案中文硬编码（各 Dialog.vue） | 国际化前置条件 |
| L3 | 云同步/多设备 | WebServer 账号体系与本地配置无关联 | 战略级，依赖账号体系成熟 |
| L4 | CLI usage 报表 | UsageTracker 有数据（`usage.jsonl`），CLI 无 usage 命令 | 桌面端已有图表 |

## 三、强化建议（现有功能，按优先级）

### 高

1. **Verification 升级为多步验证链**
   - 位置：`haoyue_runtime/Verification/BuildVerifier.cs`（现 102 行，`ResolveCommand` 已支持工作区 `VerifyCommand` 自定义 + 四类项目内置命令）。
   - 现状局限：单命令链（build/check），AutoVerify 默认开启（`AgentConfig.AutoVerify = true`）但「验证 = 能编译」。
   - 建议：支持命令数组（build → test），失败输出智能摘要（保留错误块、截断无关输出，现有 `MaxToolOutputChars` 机制可复用）。
   - 预期价值：修复-验证闭环质量直接提升，是「自动修复循环」（`MaxRepairAttempts=3`）有效性的前提。可行性高：仅改一个文件 + 配置模式。

2. **知识检索参数外置热加载**
   - 位置：`haoyue_runtime/Data/KnowledgeSearchRanker.cs`——同义词表（Synonyms）、字段权重（title 3/content 2/tags 2）、编辑距离阈值（≤6 字 k=1）均为硬编码。
   - 建议：外置为 `prompts/` 同款热加载目录（如 `~/.haoyue/knowledge/synonyms.txt`），运行时扫描重载。
   - 预期价值：垂直领域（医疗/法律/行业黑话）用户可自助增强命中率；社区可贡献词表。可行性高：项目已有成熟的热加载范式（PromptProvider）。

3. **会话搜索 RPC**（同缺失 H2）：`Daemon/DaemonAdminApi.cs` 加 `session.search`，SQLite LIKE 起步、预留 FTS5。

### 中

4. **MCP resources 接入提示链路**：`Prompts/PromptProvider` 槽位机制现成，新增 `mcp-resources` 槽位；配合 MCP 工具逐个审批（与 H3 联动）。
5. **Skills manifest v2**：`SkillManager.cs` 的 `SkillManifest` 增 `allowed-tools` / `parameters` / `triggers` 字段，向后兼容（缺省视为全允许）。
6. **Schedule 通知通道**：`ScheduleService` 完成态回调接入桌面通知（Electron Notification API 现成），失败重试策略进 `ScheduledTask` 模型。
7. **CLI 管理命令补齐**（同缺失 M6）：`haoyue_cli/Commands/ManagementCommands.cs` 模式已成熟（3 个命令文件 857 行），逐组加壳即可，走 daemon RPC 不需要新后端逻辑。
8. **Daemon 握手认证评估**：当前 Named Pipe/Unix Socket 依赖本机信任（`protocol.info` 有协议协商）；多用户主机场景可评估加 token 握手。成本低，优先级取决于部署形态。

### 低

9. **Events 持久化**：`Events/`（181 行）仅进程内；工具调用历史审计落 SQLite，支撑企业合规场景。
10. **Workspaces 模板化**：`WorkspaceManager`（276 行）初始化仅建目录；可按项目类型预置 `.haoyue/` 模板（AGENTS.md 骨架、推荐 MCP 预设——MCP 预设已有桌面端实现可复用）。

## 结论摘要

Haoyue 的 **Provider 层、Daemon 协议、内置工具、知识库、ComputerUse（含四平台驱动）** 已达到成熟水准且有测试固化；**Sessions/Scheduling/Mcp/Skills** 功能可用但存在明确边界（无搜索、无通知、resources 未注入、manifest 过简）；**Verification/Experts/Coordination/Extensions** 属最小实现。最值得投入的三个方向：**自定义专家**（线格式已预留，低成本高价值）、**会话搜索**（SQLite 现成）、**验证链升级**（AutoVerify 卖点的前提保障）。
