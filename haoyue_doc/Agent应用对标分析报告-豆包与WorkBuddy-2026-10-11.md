# Agent 应用对标分析报告：haoyue vs 豆包 vs WorkBuddy

- 日期：2026-10-11
- 评估对象：haoyue（浩玥）全仓库
- 对标产品：豆包（字节跳动，Doubao-Seed-2.0 / 4.0 客户端，2026-03 全平台推送）、WorkBuddy（腾讯系 AI 工作台，当前会话环境实证）
- 方法：基于仓库代码与 `haoyue_doc/` 已收口评估（G1-G7 全闭环、NLP/HCI 47 项 44 项落地）确定 haoyue 现状；对标侧以 2026-10 公开资料与实测为准
- 差距程度分级：**领先 / 持平 / 小幅落后 / 明显落后 / 缺失**

---

## 一、结论摘要

1. **haoyue 在 Agent 工程纵深上不落后**：工具策略闸门、bash 审计+沙箱、事件溯源、回合回滚、进化引擎、本地 GGUF 推理链路（CUDA 11 倍提速、KV 前缀复用）等能力达到或超过两款商业产品的公开能力面，其中进化引擎与可审计安全层为差异化领先项。
2. **差距集中在「产品化外壳」而非「Agent 内核」**：四维度中落后最多的不是循环/工具/纠偏，而是语音交互、多端覆盖、开箱体验、垂直创作能力、连接器生态——均为商业产品靠规模投入堆出的面，haoyue 以既有架构可以逐项补齐。
3. **最大单项风险是零配置不可用**：haoyue 首启必须手动配置 Provider 或自备 GGUF，而豆包/WorkBuddy 均开箱即用。这是把「技术合格线」变成「可用产品」的第一道坎。

## 四、逐项完善建议与收益评估

### S1 零配置不可用（高优先级）

- **建议**：三步走。① 桌面端首启向导内嵌「一键 Ollama 拉取」流程（检测本机 Ollama→自动 `pull` 一个 4B 级 Q4 模型→注册为 local provider→跑加载自检），全程一次点击；② 内置一个免密钥公共推理入口（如引导式申请页+粘贴 key 即测通），并把「三步引导」（H23）与模型配置合并为同一流程；③ `haoyue doctor` 增加「可用模型=0」的显式诊断与修复指引。
- **量化目标**：新用户从安装到首次成功对话 ≤5 分钟、配置步骤 ≤2 步；首启流失点从「配置 Provider」收敛为「无」。
- **预期收益**：**高**（决定产品可用性的单点）。
- **落地难易度**：**中**（Ollama 检测与拉取流程约一个前端向导+CLI 命令；进程内 GGUF 自动下载体积大，二期再做）。

### S2 语音交互与音视频理解（高优先级）

- **建议**：分两期。一期「语音输入」：桌面端集成 whisper.cpp（本地 ASR，与现有 GGUF 进程内推理同栈）+ 按 F1 按住说话，转写文本直接进 Composer；CLI 可选接系统听写。二期「语音输出与视频理解」：TTS 接 Windows SAPI/Piper 本地合成；视频理解用 mmproj 视觉链路做关键帧采样（每 2-5s 抽帧→批量图片输入），复用现有图片多模态通道，不引入新推理栈。
- **量化目标**：语音输入首字延迟 <1.5s（本地 small 模型 GPU）、识别准确率按 whisper 基线；视频理解支持 ≤3 分钟视频摘要任务，经 agent-eval 新增 2 个视频任务回归。
- **预期收益**：**高**（补齐与豆包差距最大的感知面）。
- **落地难易度**：一期**中**、二期**高**（视频抽帧调度与 token 预算需新设计）。

### S3 文档/表格/PPT 创作链（高优先级）

- **建议**：不重写引擎，走技能层复用既有资产：① 将 doc_toolkit 的 IR（六种块类型）反向暴露为 `doc_render` 工具（MD/HTML→docx 已有互转链路，补 pptx/xlsx 渲染器，`BaseRenderer` 一行注册机制现成）；② 仿 WorkBuddy/豆包的「文档技能」形态产出 3 个官方技能：报告生成（md→docx）、数据表生成（结构化数据→xlsx）、演示稿生成（大纲→pptx）；③ 产物统一落 `.haoyue/outputs/` 并支持桌面端打开预览。
- **量化目标**：3 类文档生成任务在 agent-eval 中成功率 ≥85%；覆盖 6 种块类型保真度验证（沿用 verify_e2e 23 项模式）。
- **预期收益**：**高**（办公是两款对标产品最高频场景，补上后 haoyue 从「开发工具」扩展为「生产力工具」）。
- **落地难易度**：**中**（docx 渲染器已有雏形，pptx/xlsx 需新写两个 renderer，纯 Python 可离线）。

### S4 Web/移动端与多端同步（中优先级）

- **建议**：① 短期做 Web 端：daemon 已有 JSON-RPC+token+契约快照，加一层 HTTP/WebSocket 网关（或直接用 haoyue_webserver 承载），前端复用 haoyue_desktop 的 Vue 组件库抽 package；② 同步先做「会话只读漫游」（会话 SQLite 定期快照到用户自选的网盘/自建对象存储），不做实时协同；③ 移动端暂缓，用 PWA 承接 Web 端。
- **量化目标**：Web 端覆盖桌面端 ≥80% 高频功能（会话/工具状态/任务/设置）；断线重连后事件重放完整率 100%（事件溯源已保障）。
- **预期收益**：**中**（扩大使用场景，但非当前目标人群痛点）。
- **落地难易度**：**高**（网关安全暴露、跨设备认证、组件抽包均是结构化工程）。

### S5 连接器生态（中优先级）

- **建议**：以 MCP 为分发格式，不另造协议：① 定义「连接器包」规范（MCP server 配置+元数据+图标+中文说明），复用技能市场站点分发；② 首发 10 个高频连接器并随官方仓库维护（浏览器、Git/GitHub、邮箱 IMAP/SMTP、日历 ICS、RSS、剪贴板、Notion 文件导出、SQLite、HTTP API 通用器、系统通知）；③ 桌面端「设置→连接器」卡片化一键启停，沿用「允许的网站」白名单的 RPC 模式（`web.allowedGet/Set` 已验证该交互）。
- **量化目标**：市场首批 ≥10 个可一键安装的连接器；连接器从发现到可用 ≤3 次点击。
- **预期收益**：**中**（生态位卡位，短期使用增量有限）。
- **落地难易度**：**中**（机制全部现成，工作在包规范与运营）。

### S6 技能市场内容量（中优先级）

- **建议**：① 以 doc_toolkit、Computer Use、进化引擎三大独有资产为题材，优先产出 20-30 个官方技能（代码审查、发布流水线、周报生成、会议纪要、数据清洗、截图 OCR 入库等，多为现有工具的组合编排）；② 技能包格式与 GitHub 单仓库分发兼容，允许社区 PR；③ 市场站点补搜索/分类/评分。
- **量化目标**：官方技能 ≥30 个（当前个位数），月度新增节奏化；技能安装到首次触发成功率 ≥90%。
- **预期收益**：**中**。
- **落地难易度**：**低**（纯内容生产，机制零改动）。

### S7 角色化子代理与团队编排（中优先级）

- **建议**：① 在 `delegate_tasks` 之上加「角色预设」：role=researcher/implementer/reviewer，注入不同提示词+工具白名单（技能系统 `allowed-tools` 机制可直接复用）；② 桌面端可视化编排：多代理面板展示并行子任务进度（事件总线已有 `BackgroundTaskEvent`，补前端渲染即可）；③ 引入「汇报模板」统一聚合报告结构。
- **量化目标**：3 个内置角色预设；多步研究类任务在 agent-eval 新增用例上成功率较单代理提升 ≥15%。
- **预期收益**：**中**。
- **落地难易度**：**低**（fan-out、文件锁、深度控制均已落地，缺的只是预设与 UI）。

### S8 深度研究模式（中优先级）

- **建议**：① 新增官方技能 `deep-research`：编排「拆解子问题→并行 web_search→逐源 web_fetch 核验→交叉引用清单→产出带引用报告」的固定流程，用多子代理 fan-out 承载；② `web_fetch` 结果落事实层（`fact_save`，带来源 URL 与置信度），利用既有 TTL 机制支持「研究快照」；③ 报告输出为 Markdown+引用脚注。
- **量化目标**：单主题研究报告端到端 ≤10 分钟（云端模型）、引用可点击核验率 100%；agent-eval 新增 1 个研究任务回归。
- **预期收益**：**中**。
- **落地难易度**：**低**（全部原语已存在，是编排层技能）。

### S9 官方嵌入 SDK（低优先级）

- **建议**：按契约快照生成 TS 客户端（`contracts/daemon-contract.json` 为单源，写 codegen 脚本产出类型化 RPC 封装+token 握手示例），发布 npm；Python 版走同一契约。
- **量化目标**：SDK 覆盖契约 100% RPC 方法；从安装到跑通首回合 ≤10 行代码。
- **预期收益**：**低-中**（第三方嵌入与自动化脚本场景）。
- **落地难易度**：**低**（契约驱动，codegen 为主）。

### S10 平台覆盖（低优先级）

- **建议**：① .NET 10 本身跨平台，补 Linux（tar.gz + deb）与 macOS（arm64 dmg）自包含发布流水线（packaging/ 已有脚本骨架）；② CLI 先行、桌面端跟进；③ CI 增加跨平台测试矩阵。
- **量化目标**：三大平台 CLI 可安装、核心 696 测试全绿；发布产物含校验和。
- **预期收益**：**中**（扩大装机面）。
- **落地难易度**：**中**（CI 与打包为主；Computer Use/SystemControl 等 Windows 特性需按平台优雅降级——已有 OS 自动识别基础）。

### S11 性能遥测面板（低优先级）

- **建议**：事件总线已记录轮次与用量，补三类度量落盘：TTFT、每回合墙钟、工具执行耗时；桌面端「用量统计」页扩展延迟分布图；`events.recent` 暴露聚合查询。
- **量化目标**：回归对比任两次提交的 TTFT/吞吐变化可一键导出；与 agent-eval 报告联动。
- **预期收益**：**低-中**（调参与性能回归的基础设施）。
- **落地难易度**：**低**。
