# Agent 架构四组件加强方案（整改后增量评估）

> 评估基准：2026-10-12/13 完成 21 项整改（H1-H4、M1-M10、L1-L7 全部闭环，797/797 测试通过）后的代码状态。
> 本文只列**新增**加强空间，不重复已修项。所有结论均经源码复核（文件:行号）。

## 一、总体判断

四组件的基础工程度已经扎实（并发安全、撤销台账、熔断重试、FTS 检索、审计留痕都已到位），剩余缺口可归为三类：

1. **硬机制缺失**——策略自适应、steering 中断、bash 进程树治理等只有"软提示"没有"硬动作"，最坏情况下受 MaxSteps 约束但每次重试都真实消耗资源；
2. **成本与规模化劣化**——token 估算无校准闭环、图片跨回合重复上传、DB 无保留策略，问题随会话变长/用量变大而加剧；
3. **记忆自动化断层**——"经历→记忆"链路不存在，事实/记忆写入 100% 依赖模型当回合自觉。

以下按价值排序给出 22 项加强方案。

## 二、高优先级（5 项）

### H-A【执行】bash 默认路径进程树治理 + 超时输出保留

- **位置**：`Tools/Builtin/BashTool.cs:58-77`（非沙箱路径）、`Configuration/HaoyueConfig.cs:276`（沙箱默认 false，已复核）
- **现状**：默认走 CliWrap `ExecuteBufferedAsync(cts.Token)`——CliWrap 取消语义**只杀父进程**，超时后孤儿孙子进程（`npm start &`、`dotnet build` 派生子进程的场景）无限消耗资源；且超时直接 `ToolResult.Fail`，**已产生输出全部丢弃**。M9 的"超时保留输出"只在沙箱路径（`DrainQuietly`）生效，而沙箱默认关闭。`BashRiskClassifier` 已算出 High/Medium 风险等级，但只进审计、不驱动执行决策。
- **建议**：① 非沙箱路径加 `killEntireProcessTree: true`（一行）；② 分级沙箱——分类器判 High 的命令自动套 `WindowsJobObject`（类已存在，不依赖全局开关）；③ 非沙箱路径改 `ListenAsync` 增量收集，超时回传部分输出，与沙箱路径语义拉齐。
- **预期效果**：消除孤儿进程；模型超时后拿到部分输出可诊断"超时前发生了什么"，避免盲目重试；高危命令获得进程树/内存/进程数限制而不必全局开沙箱。
- **工作量**：小（①）/ 中（②+③）

### H-B【感知】工具结果 head+tail 截断

- **位置**：`Tools/ToolTypes.cs:101-102`（`Truncate` 仅保头 30k 字符），影响 `BashTool.cs:70`、`FileTools.cs:183`、`SearchTools.cs`、`Mcp/McpManager.cs:477`
- **现状**：所有工具输出统一"保留头部、丢弃尾部"。而 `dotnet build`/`pytest`/grep 的失败摘要、exit code、统计几乎总在输出**尾部**；`knowledge_search` 最多 20 条 ×600 字符（约 13K）在 32K 窗口模型上超预算 3 倍且不走 `context.Truncate`；`web_fetch` 的 `max_chars` 是模型可控绝对常量，绕过窗口预算。
- **建议**：`Truncate` 增加 `TailPrioritized` 变体（head+tail，中间折叠并标注省略量；非零退出码时 tail 优先）；`knowledge_search` 套 `context.Truncate`；`web_fetch` 上限改为 `min(模型请求值, ToolOutputBudget 派生值)`。
- **预期效果**：构建/测试失败诊断信息不再被系统性丢弃，直接减少"看到腰斩输出→误判→重试"循环；检索/抓取类工具收敛进窗口预算。
- **工作量**：小-中

### H-C【记忆】 ConsolidationRunner：会话经历自动沉淀为记忆

- **位置**：现状缺口——`Evolution/ReflectionRunner.cs:118` 的反思输入是 `DefectAggregator` 缺陷报告、产出是技能草稿，不碰 facts/knowledge；`FactSaveTool`/`MemorySaveTool` 是唯一写入口，全靠模型当回合自觉（已复核）
- **现状**：全仓无 reflect→fact / consolidate / distill 链路。模型没主动调 fact_save 的会话，踩到的坑、用户的偏好全部沉底，`fact_search` 也搜不到。
- **建议**：新增 ConsolidationRunner，**复用 Evolution 引擎现成基础设施**（隔离回合、JSON 契约输出、人工审批、anti-self-feeding）：`ScheduleService` 定时扫描近期会话（messages_fts 已可定位）→ 提炼候选事实（带 confidence/TTL/topic）→ 与 facts.json 去重合并 → 低置信候选走桌面端确认。另加触发式沉淀：回合结束若 `TurnExecutionScope` 显示有重要变更/修复而本回合未写记忆，注入一次性提示。
- **预期效果**：记忆系统从"模型自觉"进化为"自动沉淀"，跨会话学习断层打通；这是记忆组件从可用到好用的分水岭。
- **工作量**：大（基础设施齐全，主要是提示词契约 + 合并逻辑 + 确认 UI）

### H-D【决策】策略自适应硬机制：失败工具隔离

- **位置**：`Agents/Agent.cs:181-239`（`HandleToolResult`）、`Agent.cs:53-63`（阈值常量）
- **现状**：同一签名连续失败 2 次注入 repeated-failure 提示、4 次注入 strategy-pivot 提示——全部是 user 角色文本，模型可无视。回合内没有故障工具隔离、模式强制降级、换将（委派干净上下文子代理）这类硬动作。"模型摆烂重试 20 次同一命令"只受 MaxSteps=40 约束。
- **建议**：`HandleToolResult` 加硬升级阶梯——同签名失败达到 strategy-pivot 阈值后：① 该工具加入**回合级黑名单**（`ExecuteToolAsync` 解析后直接返回 "tool quarantined this turn"，可复用 `FilteredToolRegistry` 思路）；② auto 模式下可选把剩余工作委派给全新子代理（上下文干净，避免锚定）。
- **预期效果**：失败循环有硬上限，最坏情况的时间/token 消耗从"40 步全烧"降到阈值即刹车；与 H-B 叠加进一步减少无谓重试。
- **工作量**：中

### H-E【感知】token 估算实测校准闭环

- **位置**：`Agents/ContextPlanner.cs:29-36`（EstimateTokens 纯启发式 Latin 4.0 / CJK 1.5 字符每 token）、`:83-87`（`EstimateTokens(ChatMessage)` 不含 Thinking）、`:178-188`（WindowBudget 不减工具 schema）
- **现状**：真实 prompt tokens 每次都有——`ProviderManager.cs:487 RecordUsage` 记录 `InputTokens` 并持久化，但**没有任何代码把 actual vs estimated 偏差反哺估算系数**（M7 的 Calibrator 只在超限报错后救火）。且两块大头不进预算：工具定义 JSON（注释自承认"tool manifest alone is thousands of tokens"）和 DeepSeek reasoner 每轮回传的 reasoning_content。代码密集文本偏差可达 ±50-100%：低估→超限 400，高估→窗口浪费、过早压缩。
- **建议**：① per-model 实测校准——请求后算 `ratio = actual/estimated`，EWMA 平滑持久化（一张 `model_token_stats` 表），EstimateTokens 按模型乘系数，数据链路已存在只差反馈环；② `EstimateTokens(ChatMessage)` 计入 Thinking；③ WindowBudget 增加工具 schema 估算项（按 promptKey 缓存避免每步重算）。
- **预期效果**：同时缓解"超限 400"和"窗口白白浪费/过早压缩"两个方向的问题；长任务的历史保留更稳。
- **工作量**：中

## 七、实施记录（2026-10-14，批次 C/D + 收尾项全部落地）

本方案 9 项加强（H-A、H-B、H-D、M-B、H-E、M-C、M-D、L-D、H-C）已全部实施并通过测试。逐项记录如下（含与建议方案的偏差）。

### H-A【执行】bash 进程树治理 + 超时输出保留 —— 已实施（①③，②未做）

- `Tools/Builtin/BashTool.cs` 整文件重写非沙箱路径：CliWrap → 自托管 `Process`（`ExecuteDirectAsync`）。**偏差说明**：方案假设的一行 `killEntireProcessTree: true` 在 CliWrap 3.10.3 不存在（上游 issue 仍开放），故自托管实现：
  - Windows：复用现有 `WindowsJobObject(0, 0, false)`（零限制 = 仅 kill-on-close 兜底），超时/取消时 `job.Dispose()` 杀整树；
  - Unix：`setsid` 进程组隔离 + libc `kill(-pgid, SIGKILL)` P/Invoke（新增 `ProcessGroupKill` internal 类）；
  - 超时后 `DrainQuietly` 回收已产生输出，outcome 统一为 completed/timeout/failed；失败命令输出走 tail-prioritized 截断（与 H-B 叠加）。
- 未做②（分类器判 High 自动套 Job）：保留为后续特性，当前 kill-on-close 已覆盖孤儿进程问题。

### H-B【感知】工具结果 head+tail 截断 —— 已实施

- `Tools/ToolTypes.cs` 新增 `TruncateTailPrioritized(text, label, tailShare)`（tailShare 钳制 0.1..0.9，中间折叠标注省略量）。
- 应用点：`BashTool`（失败命令 tailShare 0.7）、`DelegateTool`、`DelegateTasksTool`、`FileTools.read_file`、`McpManager`、`KnowledgeTools`、`WebTools`（`max_chars` 上限改为窗口预算派生 + 超长折叠改 head+tail）。

### H-D【决策】失败工具回合级隔离 —— 已实施

- `Agents/Agent.cs`：`quarantinedTools` HashSet；`HandleToolResult` 在 strategy-pivot 阈值分支把工具加入隔离并 publish WarningEvent。
- `Agents/Agent.Tools.cs`：`ExecuteToolAsync` 解析后检查隔离，返回 "quarantined for the rest of this turn" 失败结果。
- 未做②（auto 模式换将委派）：隔离已打断失败循环，换将留待后续。

### M-B【决策】steering abort 中断在途批次 —— 已实施

- `Agents/AgentSteeringQueue.cs`：`RequestAbort()` / `IsAbortRequested`（显式 opt-in，默认语义不变）。
- `Agents/Agent.cs`：循环顶部 drain 后 + 工具批次 foreach 内每个 call 前检查 abort，break 并 publish 事件。
