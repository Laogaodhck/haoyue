### 评测前发现并修复的 2 个 runtime 阻断性缺陷

模型接入过程本身暴露了两个只有真实加载才能发现的问题，均已修复：

1. **Gemma 4 聊天模板无法应用（阻断级）**：官方模板使用 llama.cpp 内置 Jinja 尚不支持的语法（`namespace`、`raise_exception` 等），`llama_chat_apply_template` 直接失败，CLI/运行时对该 GGUF 完全不可用。
   修复：`LocalLlmClient.BuildPrompt` 增加 `RenderCanonicalPrompt` 兜底——apply 失败时按架构走 canonical 渲染（gemma4：`<|turn>role\n…<turn|>`，思考开关注入 `<|think|>`），未知架构如实抛错。分词探针验证：全部标记按特殊 token 正确编码（`<turn|>`=单 token 106），BOS 恰好注入一次。新增 4 个单元测试，`dotnet test` 18/18 通过。
2. **KV 复用第二次请求必崩（严重）**：`LocalModelCache.StoreReuse` 把 `TryGetReuse` 返回的同一个 entry 存回时先 `Dispose()` 了同对象 Context，导致开启 `localPrefixReuse` 后第二轮请求命中已释放 context（`ObjectDisposedException`）。修复：仅当新旧 entry 非同一对象时才释放旧 Context。本地多轮 Agent 回合此前只要开 KV 复用必触发。

## 2. 任务一：对话流畅性测试

3 个多轮场景（A 信息记忆 5 轮 / B 概念深挖 4 轮 / C 干扰回跳 5 轮），量化指标：设计检查点命中率（关键词组）、字符级 distinct-2 自重复率、跨轮 8-gram 复读、长度波动系数。

| 场景 | 检查点命中 | avg distinct-2 | min distinct-2 | 长度波动 | 跨轮复读 |
|---|---|---|---|---|---|
| A·信息记忆与追问 | **100%**（14/14 组关键词） | 0.947 | 0.866 | 0.79 | 0 |
| B·概念解释深挖 | **100%** | 0.865 | 0.799 | 0.55 | 0 |
| C·干扰与话题回跳 | **100%** | 0.906 | 0.883 | 0.48 | 14* |

\* 场景 C 第 5 轮被要求"复述 3 个主题方向"，14 个共享 8-gram 属于**合法引用**（复述原文标题必须重复），非复读缺陷。

### 发现

- **上下文记忆可靠**：姓名/店名/地址三要素在间隔多轮后完整复述；术语跨轮一致（向量数据库场景 B 检查点全中）。
- **抗干扰良好**：插入天气、火锅广告语两轮无关话题后，回跳正确推荐了首轮主题之一并给出一致理由。
- **回跳保真度会衰减（主要问题）**：第 5 轮复述第 1 轮 3 个主题时，模型只忠实还原 2 个，第 3 个自行编造（"原计划的第三个主题，为补充完整"）——4B 模型对长列表细节的召回不是逐字保真的，长会话中依赖模型复述历史存在风险。
- **无复读循环、无模板句复读**：全部轮次 max-run 检测无 ≥3 次重复片段（`RepeatPenalty=1.1 / PenaltyCount=64` 采样配置有效）。

## 3. 任务二：响应速度测试

### 3.1 不同输入长度（KV 复用自然命中，输出约 40 token）

| 输入 | prompt tok | TTFT | 预填充速度 | 解码速度 | 总耗时 |
|---|---|---|---|---|---|
| 短 | 87 | 1.38 s | 63 tok/s | 7.3 tok/s | 5.1 s |
| 中 | 605 | 9.05 s | 67 tok/s | 7.6 tok/s | 13.9 s |
| 长 | 2296 | 31.0 s | 74 tok/s | 7.2 tok/s | 36.3 s |

### 3.2 KV 前缀复用收益（1180 tok 共享手册 + 两轮提问）

| 用例 | TTFT | cached tok | 等效预填充速度 |
|---|---|---|---|
| 冷基线·首问 | 20.5 s | 2 | 57 tok/s |
| **复用命中·第二问** | **0.61 s** | **1237** | 2062 tok/s |
| 冷对照·标记破坏复用 | 22.1 s | 4 | 58 tok/s |

- **TTFT 20.5 s → 0.61 s，约 33 倍**，冷对照证明收益真实来自前缀复用而非缓存巧合。
- 解码速度稳定在 7.2–7.6 tok/s，与输入长度无关；TTFT 与 prompt 长度线性相关。
- 模型冷启动（磁盘冷读 + 权重重排）实测最长约 7.5 分钟，页缓存命中后 5–8 秒——桌面端冷启动体验是需要优化的点。

## 4. 任务三：自我修正与持续学习机制

### 4.1 已实现的机制（`benchmarks/local-model-eval/SelfCorrectionEval.cs`）

```
生成 → 错误检测（规则检测器 + 模型自评 JSON 双通道）
     → 反馈修正（问题清单注入重新生成，最多 2 轮）
     → 知识积累（确认问题 → Lesson 指纹去重 → lessons.json 持久化）
     → 下次生成注入相关 lesson（持续学习闭环）
```

- **规则检测器**（确定性，零推理成本）：空回复、复读循环（12 字片段 ≥3 次）、违反"不超过 N 字"约束（正则提取约束）。
- **模型自评**：同一模型以低温度输出严格 JSON（pass/score/issues），宽松解析，自评输出不可解析时不判罚（防误杀）。
- **LessonStore**：按 `类别|关键词` 指纹去重，同类问题命中数递增；检索按关键词匹配注入 system 提示。数据资产与 runtime 进化引擎（DefectAggregator→ReflectionRunner→技能草稿）同构，可直接迁移。

### 4.2 真实模型验证结果

| 用例 | 外部 ground truth | 结果 |
|---|---|---|
| 算术自检（37+51+102） | 答案含 190 | **round 1 即正确**，自评无误判 |
| 错误前提纠正（《红楼梦》作者） | 应指出曹雪芹、不附和 | **主动纠正**，未附和用户错误前提 |
| 字数约束（≤30 字） | 规则检测 | 检测闭环 100% 生效（3 轮全部检出并反馈），但模型 3 轮输出 43–55 字，**未能收敛达标** |

- 注入 lesson 复跑验证：知识积累闭环成立（lesson 命中数 3→5、相关 lesson 成功注入提示词、首轮输出字数 49→43 改善），但 4B 级模型对"精确数字数"这类元认知任务修正能力不足——**机制检测与积累有效，修正上限受模型能力约束**。
- 自评通道与规则检测器结论一致（同为 length_violation），双通道无冲突判罚。

## 5. 改进建议（按优先级）

1. **【已完成】runtime 兜底渲染 + KV 复用生命周期修复**——新 GGUF 模板超前于 llama.cpp Jinja 支持是常态，建议每次引入新模型跑一次 `probe` 分词探针确认标记编码。
2. **解码吞吐**：7.3 tok/s 是当前主要体验瓶颈。装 CUDA 后端（`-p:LlamaBackend=Cuda12` 构建 + `gpuLayers=999`）预计 5–10 倍提升；纯 CPU 路径可试 `flashAttention=true` + `kvCacheQuantization=q8_0`（KV 2.4 GB→更小，注意力内核加速）。
3. **冷启动**：7.5 分钟冷加载对桌面端不可接受。建议启动后台预热常用模型，或降配窗口（32k→8k 可显著缩短 mmap 页入与 KV 分配）。
4. **字数类指令约束**：机制层可加"硬性后处理"（检测超限时截断/要求重写并显式给字数），不要依赖 4B 模型自我计数；或对本地模型在系统提示里把字数约束转述为"不超过 2 句话"这类可执行粒度。
5. **长会话保真**：场景 C 暴露的列表复述失真，建议 Agent 层对关键事实（姓名、参数、清单）用 KnowledgeStore/会话侧账本兜底，不完全信任模型召回。
6. **自评成本**：自评多花一次推理（本机约 8–15 s）。建议规则检测先行、自评仅对高风险输出（工具调用前、代码变更后）启用，与 runtime 现有 BuildVerifier 验证链互补。
7. **评测可复跑**：harness 支持 `all|fluency|speed|selfcorrect|probe` 分相运行；换模型只需改 `EvalCore.ModelFile`。建议纳入新本地模型上机的标准流程。
