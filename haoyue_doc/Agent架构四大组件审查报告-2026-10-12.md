### 1.2 主要缺陷

1. **图片负载无治理（系统性缺口）**：截图原样 base64 PNG 回填，无 resize/降采样；图片不计入任何输出预算，`FitInjectedText` 只处理文本，多图回合可把 `FitToWindow` 打到"单消息超预算"的最后手段分支且无法收缩。
2. **`read_file` 无二进制检测**：grep 有 `IsProbablyBinary` 防护，read 没有——读二进制文件会把乱码灌进上下文，防护不对称。
3. **`web_fetch` 非 HTML 内容不分支**：PDF/图片 URL/JSON API 一律过 HTML strip 管线，二进制内容变乱码文本。
4. **ContextWindow 声明无校正闭环**：完全信任用户声明的窗口大小，`TokenUsage` 已采集（`ChatTypes.cs:117-129`）但未反哺 `ContextPlanner`；声明错误直接导致溢出。
5. 压缩每回合至多一次（`compactedThisTurn`），超长回合后半段再触顶只能硬裁剪；压缩是持久性改写（`ReplaceHistory`），被摘要的细节不可恢复；持久化失败时内存/磁盘历史漂移。

### 1.3 接口与数据流

健康。全程中立 `ChatMessage`/`ChatImageAttachment` 模型，provider 差异隔离在三个 client；错误四层传播（工具异常→`ToolResult.Fail` 可自纠 / LLM→`LlmException` / 感知基础设施→WarningEvent 降级不中断回合 / 孤儿工具轮→发送前修复为显式失败）。无数据丢失、无循环依赖。

### 2.2 主要缺陷

1. **PlanTool status 无枚举校验**：schema 声明 pending/in_progress/completed，但执行时任意字符串照单全收；`TurnPlanStep.Completed` 只认 `"completed"/"done"`——模型写 `"done✅"` 之类会使 AllCompleted 永不成立，plan-finished 纠偏失效。
2. **失败签名归并缺陷**：不可修复的畸形参数经 `ToolArguments.Sanitize` 统一归为 `"{}"`——同一工具两次**不同**畸形调用被误判为同签名连败，提前触发策略纠偏提示。
3. **wrap-up 期纠偏竞争**：no-progress 守卫避让 wrap-up，但 plan stale / redundant call / answer completeness 无避让，可能在强制总结轮注入干扰提示挤占最后输出预算。
4. **`delegate_tasks` 超量静默截断**：>6 任务直接 `Take(6)` 不报错，模型不知道任务被丢弃。
5. **修复循环预算死提示**：验证只在模型自认完成且 mutated 时运行；wrap-up 轮若改了文件会注入修复提示，但步数预算已耗尽，修复轮立即被拦截——出现"注入了修复提示却永远执行不了"的死循环提示。
6. 本地 `ThinkTagParser` 开标签为 `" thinking"`（带前导空格）且依赖 `prompt.EndsWith(" thinking")`，与 llama.cpp 模板渲染形态强耦合，换模板家族易静默失效，无单测覆盖此耦合。
7. `AdaptiveInferenceTuner.Adjust` 的 `overrideCooldown` 参数从未使用（死参数，意图未实现）。

### 2.3 接口与数据流

健康。决策与感知/执行/记忆解耦清晰：历史只在追加/压缩时变更，裁剪自愈发生在"发送前的请求副本"上；`ToolExecution.ToolMutated` 驱动验证/修复/完整性守卫；取消经 CT 级联到子代理。无循环依赖。

### 3.2 主要缺陷

1. **文件工具无工作区路径边界校验（最高危，已亲自复核确认）**：`ToolContext.ResolvePath`（`ToolTypes.cs`）对绝对路径直接 `Path.GetFullPath` 返回——`write_file`/`edit_file` 写 `C:\Windows\...`、`~/.ssh/...` 等工作区外路径**不会被拒绝**，默认 edit 模式下可写任意可访问路径，也没有对 `.git/`、`.env` 等敏感目标的保护。
2. **Bash 防护是黑名单正则**：`python -c`、`node -e`、`powershell -EncodedCommand`、base64 管道等解释器逃逸完全不命中；`curl -o x.sh && sh x.sh` 两段式绕过 `curl|sh` 模式；`agent.toolPolicy.enabled=false` 可关掉全部守卫。配合沙箱默认关闭，edit 模式实际安全边界主要靠内置守卫的保守性。
3. **无人工审批（HITL）环节**：策略门通过/拒绝全自动，无"用户确认后执行"关卡。
4. 沙箱超时路径返回空输出——超时前已产生的 stdout/stderr 丢失，模型无法诊断；stdout 用 `ReadToEndAsync(CancellationToken.None)` 不响应取消。
5. `ReadFileTool` 全同步，`File.ReadLines` 不响应取消，大文件上用户中断无法及时生效。
6. **审计只覆盖 bash**：MCP 调用、文件写入、web 访问均无审计轨迹；审计 IO 失败静默吞掉无告警。
7. `ToolArguments.Parse` 截断修复可能"修复"出语义错误的参数（command 被截断后照常执行）。
8. `job.Assign` 在 `process.Start()` 之后，有极小未覆盖窗口；Job UI 限制设置失败静默忽略。

### 3.3 接口与数据流

健康。`ToolResult{Output, Summary, Diff, FilePath, Images}` → `ChatMessage.ToolResult` 回填会话，错误统一以工具消息文本回传（附可操作建议），模型可自纠；`ToolMutated`/`Changes` 驱动决策层守卫与撤销。无格式不一致。

| 知识库            | SQLite 三级（notebook→source→chunk）+ 向量混合检索（词法 0.6 + 余弦 0.4；CJK bigram + 同义词热加载 + 编辑距离兜底） | `Data/Knowledge*.cs`（10 个文件）                                |
| 事件日志           | SQLite events 环形 5000 条，`JournaledEventBus` 装饰器透明持久化                                   | `Data/HaoyueDatabase.cs:67-107`、`Events/EventJournal.cs`    |

注入机制：MEMORY.md 与 facts 每回合注入（PromptSlot.Memory 槽，24k 总预算 + DegradeRank 降级链），知识库靠 `knowledge_search` 按需检索。迁移：legacy JSONL 导入 + `EnsureColumn` 渐进加列。

### 4.2 主要缺陷

1. **幽灵工具 `fact_search`**：`FactSaveTool.cs:50` 明确告诉模型"用 fact_search 可按需检索"，但该工具**不存在**——提示-能力不一致直接误导模型行为；同时 `FactsStore.Forget` 无生产调用方（没有 fact_forget 工具），模型无法撤销写错的事实，只能等 TTL 或 100 条淘汰。
2. **知识向量无失效机制**：`KnowledgeStore.Save`（更新内容）与 `Delete` 均不触碰 `knowledge_vectors`——更新后语义检索继续用旧向量；删除后向量行成永久孤儿（无 FK），持续膨胀。
3. **MEMORY.md 非原子写**：`MemorySaveTool.cs:43` 直接 `File.WriteAllText`，崩溃可产生半截文件，且是用户策展内容无备份；幂等检查只做整行 Contains，措辞稍异即重复写入，文件无限增长。
4. **FactsStore 无锁竞态**：Add/Forget 是无锁 Load→Modify→Save，CLI 与 daemon 并存时两进程同时写 facts.json 会丢更新（后写覆盖先写）。
5. 会话搜索按 payload JSON LIKE 全表扫描（无 FTS），且与 System.Text.Json 转义行为强耦合，编码器一变搜索即静默失配。
6. 事实层每回合全量注入（非检索式），无相关性过滤，多工作区长期使用后注入成本线性增长。
7. `HaoyueDatabase.Rebuild()` 无确认 drop 全部持久表（sessions/knowledge/events）。
8. 知识库工具 `RequiresWorkspace => false`（global scope 可存知识）而事实层强制要求工作区——可见范围规则不一致（设计选择但值得知晓）。

### 4.3 接口与数据流

依赖方向健康，**无循环依赖**（Data 层不反向依赖 Agents；工具经 `BuiltinTool(IPromptProvider)` 依赖提示层）。会话消息中立格式隔离 provider 差异。一处不一致：Data 层统一用 `ScopeKey/PathKey`（大小写归一）生成键，事实层却用裸路径拼文件——两套键体系并存，各自内部一致。

## 五、汇总与优先级建议

### 总体判断

四大组件均已真实实现且工程化程度高：感知有三级预算体系与 CJK 感知估算，决策有硬/软约束分层与完备终止条件，执行有四层权限与撤销台账，记忆有五层存储与混合检索。数据流整体健康——全程中立消息模型、错误分层传播、依赖方向单向、无循环依赖、无数据丢失路径。`TurnExecutionScope` 并发安全、委派真子代理、通知前缀防伪造等细节均已验证到位。

**对整体稳定性的影响**：当前最可能造成实际损害的不是功能缺失而是两类问题——(a) 安全边界（路径越界写入 + Bash 黑名单可绕过 + 沙箱默认关 + 无 HITL），(b) 提示-能力不一致（fact_search 幽灵工具直接误导模型）。其余缺陷多为边角场景或性能退化，不影响主路径。

- **Schema**（`HaoyueDatabase`）：`messages_fts` FTS5 虚表（trigram 分词——unicode61 对 CJK 整段成 token 无法短语匹配，trigram 支持子串命中）+ `AFTER INSERT`/`AFTER DELETE` 触发器与 messages 表保持同步（ReplaceHistory/Truncate/级联删除全部覆盖，无额外同步点）。json1/FTS5/trigram 不可用时整体跳过（建表+触发器同一守护块，部分失败即整体丢弃），Search 自动退回 LIKE 扫描。
