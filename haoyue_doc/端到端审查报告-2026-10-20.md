## 2. 问题清单

> 分级定义：**致命** = 交付/CI 直接失败或数据不可逆损坏；**严重** = 核心功能不可用或安全边界被突破；**一般** = 特定场景功能异常/可观测性缺失；**轻微** = 健壮性、体验、流程改进。

### 2.1 致命（1 项，已修）

#### F-1 `dotnet restore --locked-mode` 必然失败，CI 的 dotnet 作业与 release 前置门禁全部红

- **位置**：`haoyue_runtime/packages.lock.json`、`haoyue_cli/packages.lock.json`（以及被连带污染的 agent-eval / local-model-eval / cli_tests / tests 锁文件）
- **现象**（实测）：
  ```
  error NU1004: 项目的运行时标识符已更改。项目的运行时标识符: ，锁定文件的运行时标识符: win-x64。
  error NU1004: 找到项目目标框架 net10.0 的新包引用 LLamaSharp.Backend.Cpu。包锁定文件与项目依赖项不一致…
  error NU1004: net10.0 的包引用已更改。锁定文件的包引用: Markdig:[1.3.2, ), Microsoft.NET.ILLink.Tasks…
  ```
- **根因**：锁文件最后一次是在 `-p:LlamaBackend=Cuda12 -r win-x64` 下生成的，被提交进仓库：
  - `LLamaSharp.Backend.Cuda12` 记为 `Direct`，`LLamaSharp.Backend.Cpu` 降级为 `CentralTransitive` —— 而 csproj 默认（无 `-p:LlamaBackend`）引用的正是 `Cpu`；
  - 多出一组 `net10.0/win-x64` RID 快照，而不带 RID 的还原（CI 与日常开发）没有这个 RID。
- **影响**：`.github/workflows/ci.yml` 的 `Restore (locked mode)` 是 dotnet 作业第一步，失败即后续 build/test/coverage 全不执行；`release.yml` 同源受影响。
- **修复**：按 CI 口径重算锁文件（`dotnet restore Haoyue.slnx --force-evaluate`，无 RID、默认 CPU 后端），得到 36 条目的单一 `net10.0` 组、`LLamaSharp.Backend.Cpu` 为 `Direct`。修复后 `dotnet restore Haoyue.slnx --locked-mode` **exit 0**。默认 `dotnet build`（CPU）不再改写锁文件。
- **残留（转 L-8）**：用 `-p:LlamaBackend=Cuda12` 构建（本机 GPU 开发/打包的推荐姿势）仍会重写锁文件——这是「一个锁文件无法同时描述两种后端」的结构性限制，不属可自动修复范围。

### 2.2 严重（5 项，已全部修复）

#### S-1 剪贴板写入与系统通知的 PowerShell 脚本拼错，Windows/macOS 功能全坏并存在命令注入

- **位置**：`connectors/servers/haoyue_local_server.py:173`、`:212`、`:227`
- **问题**：`{[json.dumps(x)]}` 是**「包含一个字符串的 set 字面量」**，f-string 渲染出 `{'C:\tmp\x.txt'}`（Python set repr，带花括号），不是 JSON 字符串。
- **实测对照**（PowerShell 5.1）：
  - 旧写法 `Get-Content -Raw -Encoding UTF8 {'…\ps_quote_test.txt'}` → `Get-Content : 无法评估参数"Path"，因为其参数被指定为脚本块`
  - 新写法 `… '…\ps_quote_test.txt'` → 正确输出 `hello 中文`
- **影响**：`clipboard_write`（Windows）、`notify_send`（Windows 气泡 / macOS 通知）100% 失败；同时 `title`/`body` 未经转义直接内联进 `-Command`，是命令注入面。
- **修复**：新增 `_ps_quote()`（PowerShell 单引号字面量，内部 `'` 双写）；Windows 两处改用 `{_ps_quote(...)}`，macOS 改回 `{json.dumps(...)}`（AppleScript 需要的是双引号字符串）。注入用例 `x'; Remove-Item C:\ -Recurse; '` 转义后为 `'x''; Remove-Item C:\ -Recurse; '''`，不再逃逸。

#### S-2 `http_request` 接受 `file://`，只读连接器可读任意本地文件（绕过 PathGuard）

- **位置**：`connectors/servers/haoyue_local_server.py:321-329`
- **问题**：`urllib.request.urlopen` 默认装载 `FileHandler`/`FTPHandler`/`DataHandler`，因此 `file:///C:/Windows/win.ini` 可直接返回本地文件内容。`_fetch_text` 对 `file:` 的支持是 ICS/RSS 的合法需求，但 `http_request` 是「通用 HTTP 调用器」，6 个连接器把它标为只读工具，只读模式下模型仍可调用。
- **影响**：只读沙箱里出现「全盘任意读」，且不受 `PathGuard` 约束。
- **修复**：`http_request` 增加 scheme 白名单（仅 `http`/`https`），实测 `file://`、`ftp://`、`data:` 全部被拒（`ValueError: 仅支持 http/https`）。`_fetch_text` 的本地文件能力保留（ICS/RSS 依赖它）。

#### S-3 `declare_skill` 完全失效：提示词缓存键不含本回合声明集

- **位置**：`haoyue_runtime/Agents/Agent.cs:391-406`（`promptKey`）+ `Skills/SkillManager.cs:108-143,234-247`
- **问题**：技能正文由 `skill-bodies` 贡献在**合成系统提示时**读取 `_turnDeclared`。Agent 按 `promptKey`（provider/model/tools/mode/personality/language/verify/expertId）缓存 `cachedSystemPrompt`，**不含声明集**。于是模型 `declare_skill` 之后，后续 step 继续复用声明前合成的 prompt → 技能正文永不进入上下文；而 `ResetTurnDeclarations()` 在**每回合开始**清空，声明也活不到下一回合。净效果：工具返回「已加载」，实际零效果。
- **修复**：
  1. `ISkillManager` 新增 `IReadOnlyList<string> TurnDeclaredSkills()`（带默认实现，测试桩无需改），`SkillManager` 返回排序后的声明集；
  2. `promptKey` 追加 `declaredSkillsKey`。技能段本就位于 `PromptSlot.Skill`（最后一段），key 变化只在声明发生的那一刻重合成一次，前半段前缀缓存仍稳定——不违反「技能段必须最后」的缓存红线。
  3. `SkillManifestV2Tests` 增加断言：声明后 `TurnDeclaredSkills()` 可见，重置后为空。

#### S-4 stdio MCP 无写互斥，只读工具并行执行会交错写坏 JSON-RPC 帧

- **位置**：`haoyue_runtime/Mcp/McpTransport.cs:216-221`（`StdioMcpTransport.SendAsync`）
- **问题**：`StreamWriter` 非线程安全；`McpClient` 不串行化发送；而 `Agent.Tools.cs:23-42` 的 `ExecuteReadOnlyBatchAsync` **最多 4 路并行**执行只读工具。同一个 MCP 服务器被两个并行调用命中时，两帧会交错写进同一条 stdin，服务器读到半行 JSON 后整条连接失步（后续所有调用失败，且报错指向「服务器异常」）。
- **修复**：`SendAsync` 加 `SemaphoreSlim(1,1)` 单帧原子写（写+flush 在锁内）。不在 `DisposeAsync` 里释放该信号量，避免排队中的发送抛 `ObjectDisposedException` 掩盖真实断连原因（已注释说明）。

#### S-5 进化反思在多缺陷场景下：候选被移走后判失败，并把整批记录覆盖成 Failed

- **位置**：`haoyue_runtime/Evolution/ReflectionRunner.cs:180-203,418-472`
- **问题**：`action=new-skill/revise-skill` 时**对每条 pending 缺陷各调用一次** `PromoteCandidate`。第一次 `Directory.Move(draft, destination)` 已把 labs 草稿移走，第二次找不到 `skill.yaml` → 返回错误 → `RecordFailed(pending, …)` 把**包括刚记为 Candidate 的那条**在内的整批指纹改写成 `Failed`。结果：磁盘上有候选目录、账本全是失败、这批指纹再也不会被重试（进化引擎「越用越好」的核心路径静默失效）。
- **修复**：一次反思只提升一次候选，随后把同一候选路径写进所有 pending 指纹的 `Candidate` 记录；`rationale.md` 逐条记录每个缺陷的指纹/类型/来源会话。新增回归用例 `RunAsync_NewSkill_TwoPendingDefects_ShareOneCandidateWithoutFailing`（两个不同签名的缺陷簇 → `Candidates==2`、`Error==null`、单一候选目录、两条溯源）。

### 6.1 M-6 隔离运行时开销压测：结论「维持现状」

方法：Release 构建，`HaoyueRuntime.CreateIsolated` 连续 15 次采样 + 10 次分项采样，另起进程测真冷启动（临时脚手架，测完已删除，未进仓库）。

| 指标 | median | p95 | mean |
| --- | --- | --- | --- |
| `CreateIsolated`（每回合总开销） | **1.54 ms** | 6.25 ms | 1.87 ms |
| 纯 DI 容器构建（`AddHaoyueRuntime` + `BuildServiceProvider`） | 0.02 ms | 0.04 ms | 0.02 ms |
| resolve `HaoyueDatabase`（含连接） | 0.00 ms | 0.06 ms | 0.01 ms |
| `Mcp.LoadServerConfigs` | 0.05 ms | 0.58 ms | 0.11 ms |
| `Skills.Discover`（提示组装期，最多 4 次/回合） | 2.01 ms | 70 ms | 8.83 ms |
| 真冷启动（新进程首次，含 JIT + SQLite 原生库） | 227 ms | — | — |
| 同进程第二次调用 | 4.3 ms | — | — |

- 每回合注册 **27 个内置工具**，容器构建是惰性的（0.02 ms），因此「重注册 30 个工具」不是瓶颈；之前担心的「容器/注册开销」被证伪。
- 227 ms 的冷启动是**进程级一次性**成本（JIT + 原生库加载），第二个 `CreateIsolated` 就回到 4 ms；它与回合数无关，不构成复用隔离运行时的理由。
- 占云端快模型首字延迟（≈900 ms）**0.17%**，占本地 prefill（≈7 s）**0.02%**。
- 结论：**不做按 workspace 复用**。隔离运行时是并发正确性红线（技能声明、提示注册、MCP 注册互不串味），用 1.5 ms 换隔离性非常划算；把 `HaoyueRuntime` 改成可复用容器反而要引入「回合结束态重置」这类新型竞态。
- 唯一可优化点是 `Skills.Discover` 的 p95（70 ms，目录/文件系统抖动）：一回合最多扫 4 次。若后续技能数量继续增长，按目录 mtime 缓存即可（对应 ext-audit 的 P3-1），与隔离运行时无关。

### 6.3 M-7 配置委派链路：读超时与取消

`haoyue_runtime/Daemon/DaemonConfigBridge.cs` 由「`Task.Run` + `Task.Wait(4000)`」改为单条 async 流水线：

| 位置 | 改动 |
| --- | --- |
| `TryDelegateSave` | `CancellationTokenSource(4000)` 封顶；`GetAwaiter().GetResult()` 取代 `Wait`/`Result`；`OperationCanceledException` / `IOException` / `ObjectDisposedException` / `JsonException` / `UnauthorizedAccessException` / `TimeoutException` 统一返回 `false`（回落本地保存） |
| 连接 | `ConnectAsync(linkedCts)`，连接超时 1500 ms 只作用于连接阶段（区分「daemon 未启动」与「整体超时」） |
| 读 | `StreamReader.ReadLineAsync(ct)`；`config.save` 回包后 **先 `ThrowIfCancellationRequested()` 再 `store.Reload()`**，杜绝「超时后仍 Reload 覆盖本地写入」 |
| 兜底 | 用 token 注册回调主动 `Dispose` 管道：某些平台/管道的 async 读不响应 token，关闭句柄可让挂起读立刻失败，保证后台任务绝不越过 4 s |
