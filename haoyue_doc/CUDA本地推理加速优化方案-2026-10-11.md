# CUDA 本地推理加速优化方案（自适应 LLM 推理）

- 日期：2026-10-11
- 范围：haoyue_runtime 本地推理链路（`LocalLlmClient` / `LocalModelCache` / `LocalModelSettings` / `LocalModelProbe`）
- 目标：针对基于 CUDA 的本地推理场景优化 Agent 推理加速，使同一套链路能适配不同规模（小型 1~3B / 中型 7~14B / 大型 14B+ 量化）与不同上下文长度、推理能力的 GGUF 模型。

---

## 0. 现状基线（代码事实）

当前链路的关键实现，决定了优化的起点与约束：

| 事实 | 位置 | 对优化的意义 |
|---|---|---|
| 进程内 llama.cpp（LLamaSharp 0.27），单模型常驻，推理严格串行（`SemaphoreSlim(1,1)` 门） | `LocalModelCache.AcquireAsync` | 无并发批处理；单请求延迟是唯一可优化目标 |
| 三条推理路径：无状态 / KV 前缀复用 / 多模态 | `LocalLlmClient.StreamAsync` | 复用路径已实现跨请求 KV 前缀共享（`MemorySequenceRemove` 只补差异后缀） |
| 加载参数：GpuLayerCount、Threads、BatchSize(n_batch)=2048、UBatchSize(ubatch)=512、FlashAttention、KV 量化(q8_0/q4_0)、KV 卸载、统一 KV、RoPE 均已暴露且进入加载签名 | `LocalModelSettings` / `BuildLoadParams` | 大部分 CUDA 旋钮已存在，缺的是"自动选对值" |
| 加载失败重试 ×2 + CPU 降级 + 512 窗口自检，产出 `LocalModelLoadReport` | `LocalModelCache.LoadWithRetryAsync` | 已有 OOM→降级的兜底，自适应机制可复用该信号 |
| 多模态（mtmd）图像轮强制全 CPU（CUDA 后端在 Gemma4 非因果图像注意力上病态慢：266 图像 token 在 3070 Ti 上 26 分钟 vs CPU 23 秒） | `StreamAsync` 注释 | 已知 CUDA 病态路径案例；证明"GPU 不总比 CPU 快" |
| 硬件探测目前只有 GGUF header（架构/训练上下文），无 GPU/VRAM 探测 | `LocalModelProbe` | 自适应机制需要补 GPU 能力探测 |
| 观测：`TokenUsage`（prompt/generated/CachedInputTokens），无 TTFT/TPOT | `StreamReusableAsync` 等 | 需要补分段计时遥测 |

## 1. 性能瓶颈分析与定位方法

### 1.1 两个阶段的性能模型不同——这是所有优化的前提

| 阶段 | 性质 | 受限于 | 随上下文增长 |
|---|---|---|---|
| 预填充（prefill）：一次性把 N 个 prompt token 批量前向 | **计算密集**（GEMM，可并行） | 算力 FLOPS、ubatch 大小、GPU 利用率 | 线性 |
| 解码（decode）：逐 token 自回归，每步只算 1 个 token | **访存密集**（每步都要把全部权重和 KV 从显存读一遍） | **显存带宽**（GB/s），GPU 算力大量闲置 | 每步恒定，但 KV 越大带宽压力越大 |

推论（贯穿全文）：
- **prefill 慢** → 调大 ubatch / batch、检查 GPU 是否满载、检查 partial offload 造成的 PCIe 往返；
- **decode 慢** → 减少每步读取的字节数（更低比特量化、更少层数驻 CPU、KV 量化、KV 平移减少无效 KV），或用推测解码一次前向出多 token。调大 ubatch 对 decode **无收益**。

### 1.2 按代码定位的具体瓶颈点

**B1 — partial offload 的 PCIe 往返（decode 主瓶颈，中大型模型常见）**
当 `GpuLayerCount` 介于 0 和层数之间时，每一步 decode 的中间激活必须在 GPU（卸载层）与 CPU（驻留层）之间跨 PCIe 往返，同步等待把带宽优势吃得干干净净；且 CUDA 侧每层 kernel 启动固定开销在低利用率时占比显著。3070 Ti（PCIe 4.0 x16，~32GB/s 有效）往返一次就是毫秒级，足以把 decode 从 60 tok/s 拖到个位数。

**B2 — KV cache 显存占用与带宽（长上下文主瓶颈）**
KV 显存 ≈ `2 × n_layers × n_kv_heads × head_dim × ctx × bytes`（f16 为 2 bytes）。GQA 模型（n_kv_heads 远小于 n_heads）友好，MHA 老模型在 32k 上下文可达数 GB。当前 f16 + 全量 KV 驻 GPU（`OffloadKvCacheToGpu` 默认 true）是显存溢出→触发加载降级 CPU 的最常见诱因；KV 量化（q8_0/q4_0）代码已支持但依赖用户手动开。

**B3 — prefill 的 ubatch 与 GPU 利用率**
ubatch=512 对 8GB 卡偏保守：权重 5GB + KV 之后，512 token 的激活与 workspace 尚有余量时，更大的 ubatch（1024~2048）能让 GEMM 更满载、prefill 吞吐显著上升。但当前值写死为默认，无任何依据模型的探测。

**B4 — 权重量化与解码带宽（decode 的线性因子）**
decode 速度近似与"每步要读的权重大小"成反比：同模型 Q4_K_M（~4.5 bpw）对 Q8_0（~8.5 bpw）decode 提速接近 2×，prefill 也有约 1.5~2× 收益。当前量化完全由用户下载的 GGUF 文件决定，运行时无感知、无引导。

**B5 — 采样管线的 CPU 开销**
`DefaultSamplingPipeline` 每 token 在 CPU 上做 top-k/top-p/min-p/重复惩罚（窗口 64）。对小模型（decode 本身 <10ms/步）这部分可占比 20%+，表现为"GPU 空转等 CPU"。llama.cpp 原生把采样 graph 并入 GPU，LLamaSharp 托管管线则纯 CPU。

**B6 — 每 token 的托管互操作开销**
`StreamReusableAsync` 主循环每 token 构造 `LLamaBatch`、调 `DecodeAsync`（P/Invoke + Task 封装）、`StreamingTokenDecoder.Read()`。单次开销 ~0.1-0.5ms，对 decode <20ms/步的模型累计可观。

**B7 — KV 复用签名的粒度**
`TryGetReuse` 按 context 参数签名匹配，签名不同即整段丢弃重建。配置页任何一个不影响 KV 布局的字段误入签名，或 mmproj 文本轮/图片轮交替（图片轮不参与复用），都会造成大规模重复 prefill。`CachedInputTokens` 已记录命中数但未被任何自适应逻辑消费。

**B8 — 严格串行无并发**
单模型单 gate，多 agent/多会话并发时逐个排队。对单用户桌面场景可接受，但 agent 并行子任务（如多工具结果归纳）会线性叠加延迟。

### 1.3 定位方法（每类瓶颈对应的测量手段）

1. **分段计时（首选，纯托管零成本）**：在推理循环记录 `TTFT`（首个 delta 距请求起点）与 `TPOT`（生成期均摊每 token 时间），结合 `TokenUsage` 推出 prefill tok/s 与 decode tok/s。两者比值直接判定瓶颈阶段：prefill 占主导 → 查 B1/B3；decode 占主导 → 查 B1/B2/B4/B5。
2. **llama.cpp 原生日志**：`LLamaSharp` 可透传后端日志（`NativeLogConfig.llama_log_callback`），加载期输出各层 offload 明细、显存占用；`llama_perf` 数据可从 context 取（timings：`prompt eval time / eval time / runs per second`）。这是验证 B1/B3 最快的途径。
3. **GPU 侧观测**：`nvidia-smi dmon -s um`（或 NVML 托管查询）采样 GPU 利用率与显存曲线。decode 期间 GPU 利用率长期 <40% 即访存/同步受限（B1/B2/B4）；prefill 期间 <80% 提示 ubatch 不足（B3）。
4. **深挖单 kernel**：Nsight Systems 抓 trace，定位跨 PCIe 拷贝（`cudaMemcpyAsync` H2D/D2H）与低利用率 kernel。仅在静态手段无法定位时使用，日常迭代不需要。
5. **变量控制实验**：固定模型与 prompt，逐一扫描 `GpuLayerCount ∈ {0, 半量, 全量}`、`ubatch ∈ {256,512,1024,2048}`、KV 量化 `{none,q8_0,q4_0}`，绘制 TPOT/TTFT 曲面。已有基线：3070 Ti 8GB、Qwen 级 7B 量化模型、32k 上下文。
6. **复用有效性**：多轮会话对比 `CachedInputTokens / prompt tokens` 命中率，低于预期即 B7。

## 2. CUDA 优化策略与分规模适用性评估

策略按"代码改动量"分档：✅ 已支持（只差自动选值）、🔧 小改、🏗 大改。

| # | 策略 | 机制 | 改动量 | 小型(≤3B) | 中型(7~14B) | 大型(14B+ 量化) | 长上下文 |
|---|---|---|---|---|---|---|---|
| S1 | 全量 GPU 卸载 | 权重全驻显存，decode 只受带宽限制，无 PCIe 往返 | ✅ | ★★★ 首选 | ★★ 显存放得下时 | ✗ 放不下 | ★★ |
| S2 | FlashAttention | fused attention kernel，省显存+省带宽 | ✅ | ★ | ★★★ | ★★★ | ★★★ 必开 |
| S3 | KV 量化 q8_0/q4_0 | KV 显存 ÷2 / ÷4，带宽压力同比例降 | ✅（需 FA） | ★ | ★★ | ★★ | ★★★ 首选 |
| S4 | ubatch/batch 调优 | 更大 ubatch 提高 prefill GEMM 占用率 | ✅ | ★ | ★★ | ★★ | ★★★ |
| S5 | 权重量化选型引导 | 4bit 级别量化 decode 提速 ~2× | 🔧 探测+提示 | ★ | ★★ | ★★★ | ★ |
| S6 | KV 前缀复用（已有，强化） | 跨请求跳过重复 prefill，agent 多轮 TTFT 大降 | 🔧 签名治理 | ★★ | ★★★ | ★★★ | ★★★ |
| S7 | mlock/mmap 策略 | mlock 防页回收抖动；mmap 降加载峰值 | ✅ | ★ | ★ | ★★ | ✗ |
| S8 | 采样管线 GPU 化 / 轻量化 | 消除每 token CPU 采样停顿 | 🔧 | ★★★ 小模型最敏感 | ★★ | ★ | ✗ |
| S9 | 批内多 token 合批互操作 | 减少 P/Invoke 次数 | 🔧 | ★★ | ★ | ✗ | ✗ |
| S10 | 推测解码（草稿模型） | 小草稿批量起草+大模型一次验证多 token，decode 提速 2~3× | 🏃 大改 | ✗ 无草稿收益 | ★★ | ★★★ | ★★ |
| S11 | 连续批处理（continuous batching） | 多请求共享前向，吞吐 ×N | 🏃 大改 | ★ | ★★ | ★★ | ★ |
| S12 | KV 中央缓存/语义缓存 | 会话级 KV 持久化，跨会话复用 system prompt | 🏃 大改 | ★★ | ★★ | ★★★ | ★★★ |

分规模说明：

- **小型（1~3B）**：权重小，decode 每步读的字节少，瓶颈转移到 CPU 采样（B5）与互操作（B6）。S8/S9 收益最大；S1 全量 offload 后 decode 可达 80~150 tok/s，此时再压榨带宽意义不大。
- **中型（7~14B）**：8GB 卡的"最尴尬区间"——Q8 全量放不下、Q4 全量勉强。核心是 S1（配合 S5 用 4bit 量化）+ S2 + S3 的组合：权重 ~5GB 全 offload，KV 用 q8_0，32k 上下文即可稳定驻留 GPU。放不下时 S1 退半量 offload 是**最伤decode 的选择**（B1 往返），宁可 KV 留 CPU（`OffloadKvCacheToGpu=false`）也要保持权重全量驻 GPU。
- **大型（14B+，量化后仍超显存）**：S1 不可达，焦点转为"部分卸载的代价控制"（KV 全留 CPU + 权重按层比例 offload + 大 ubatch 让驻留层批量计算）与 S10 推测解码（配 0.5B~1.5B 同词表草稿模型，实测 decode 可 2~3×）。
- **长上下文（16k~32k+）**：S2+S3 是前提，S4 缓解 prefill，S12 缓解多轮 prefill 累积。

**明确不采用**：TensorRT-LLM / vLLM 自建 CUDA 图——需要脱离 GGUF 生态换模型格式，与 haoyue"用户放一个 GGUF 文件即用"的定位冲突； llama.cpp CUDA 后端已覆盖 S1~S4 全部手段，收益成本比合理。

## 3. 自适应推理机制设计（AdaptiveInferenceTuner）

### 3.1 设计原则

1. **复用现有语义**：`AutoOptimize=true`（配置页默认）时启用自适应；用户手动配置（`AutoOptimize=false`）时绝不干预——这已写在 `BuildLoadParams` 的覆盖规则里，自适应只是"auto 模式的智能版"。
2. **保守启动，观测收敛**：首次用保守参数跑通，采集遥测后再逐档调整，任何一档调整都走既有 `LoadSignature` → 权重重载 → 512 自检 → 失败回退的安全通道。
3. **有迟滞、有冷却**：调整后设冷却窗口（如 20 轮或 5 分钟），避免指标抖动导致参数震荡重载。

### 3.2 三类决策信号

**① 模型静态特征**（`GgufProbe` header + 文件元数据，已有）：
- 文件大小 + 量化位宽 → 估算参数规模档位（small/medium/large）；
- 架构与 `n_kv_heads`（GQA 与否）→ KV 显存系数；
- 训练上下文长度 → context 上限。

**② 硬件静态特征**（需新增 `GpuProbe`）：
- 通过 CUDA 后端加载期的 llama.cpp 日志解析，或 NVML/`nvidia-smi --query-gpu=name,memory.total`，获得：GPU 名称、SM 数、**可用显存**、驱动版本；
- 无 NVIDIA GPU 或探测失败 → 永久 CPU 档（等价今天 `GpuLayerCount=0`），不猜。

**③ 动态遥测**（需新增 `InferenceTelemetry`，每轮生成产出）：
- TTFT / TPOT / prefill tok/s / decode tok/s（分段计时，1.3 节手段 1）；
- `CachedInputTokens / promptTokens` 复用命中率（已有字段）；
- `LocalModelLoadReport`（降级 CPU、自检失败、加载耗时）；
- OOM / decode 失败事件（`LLamaDecodeError`）。

### 3.3 决策逻辑（分层规则 + 滑动窗口）

新增 `AdaptiveInferenceTuner`，在 `AcquireAsync` 前与每轮 `LlmCompleted` 后被调用，输出对 `LocalModelSettings` 等效字段的建议值。核心规则（按优先级）：

**第一层：装载档位（决定 GpuLayerCount / KV 位置 / KV 量化）**

```
估算显存需求 = 权重字节 + KV字节(ctx, kv量化档) + workspace余量(约0.5GB)

若 需求(f16 KV) ≤ 可用显存 × 0.9      → 全量offload, KV offload, f16 KV   [小/中模型默认]
若 需求(q8_0 KV) ≤ 可用显存 × 0.9     → 全量offload, KV offload, KV=q8_0  [中型+长ctx]
若 需求(q4_0 KV) ≤ 可用显存 × 0.9     → 全量offload, KV offload, KV=q4_0  [质量不敏感场景]
否则若 权重+小KV ≤ 显存               → 全量offload权重, KV留CPU(NoKqvOffload)
否则                                  → 部分offload: 层数≈可用显存可容纳的层数,
                                        ubatch=1024, KV留CPU；OOM降级链已有兜底
```

关键取舍固化为一句话：**权重全量驻 GPU 的优先级高于 KV 驻 GPU**——partial offload 的 PCIe 往返（B1）对 decode 的伤害远大于 KV 走系统内存。

**第二层：上下文与批（决定 ContextLength / ubatch）**
- context 取 min(模型训练值, 注册窗口, 显存档位允许值)——把现在 `BuildContextParams` 里的静态钳制升级为显存感知钳制；
- TTFT 占端到端延迟 >50% 且 GPU 利用率不足（prefill 受限）→ ubatch 逐档 +512（上限 2048）；decode 受限时不动 ubatch（无收益）。

**第三层：运行中反馈调档（滑动窗口 + 迟滞）**
- 每轮结束把遥测推进长度 10 的窗口；连续 3 轮满足以下任一才触发调整：
  - **慢**：decode tok/s < 档位目标的 60%（目标由模型规模档给出：小型 60 / 中型 25 / 大型 8 tok/s 量级）→ 尝试上一行规则中更低显存档位（释放显存）或提示量化引导；
  - **挤**：显存余量 < 10% 或发生一次 OOM 事件 → 立即（不等窗口）降一档；
  - **闲**：decode tok/s > 档位目标 2× 且显存余量 > 30% → 升一档（提升 KV 保留精度或扩大 context）；
- 每次调整后进入冷却期（20 轮），冷却期内只降档（OOM 紧急路径）不升档。

**第四层：调度方式（决定走哪条推理路径）**
- `LocalPrefixReuse` 开关：会话型请求（消息数 >2）自动走复用路径；一次性长文档请求且复用命中率 <5% 时切无状态路径（省 KV 常驻）；
- 思考预算：推理型任务（`enableThinking`）且模型 decode < 10 tok/s 时，向 agent 层上报"本地慢模型建议缩短思考预算"提示，避免 R1 类小模型把预算耗光才出答案；
- 并发请求：多请求排队时若第二层判定为小型全 offload 档，可预提示后续支持 S11 批处理（本期不实现，先留接口）。

### 3.4 与现有代码的衔接点

| 衔接点 | 方式 |
|---|---|
| `LocalModelSettings.AutoOptimize` | tuner 仅在 auto 分支生效；产出写入 `BuildLoadParams/BuildContextParams` 使用的"有效设置"对象，不改用户配置 |
| `LoadSignature` / 签名重载 | tuner 调档 = 修改有效设置 → 签名变化 → 既有重载+自检+降级通道原样复用 |
| `LocalModelLoadReport` | 降级 CPU / 自检失败作为第三层"挤"信号源 |
| `TokenUsage.CachedInputTokens` | 复用命中率，供第四层路径选择 |
| 新增 `GpuProbe` / `InferenceTelemetry` | 独立文件，`LocalLlmClient` 三条路径统一打点 |
| 前端配置页 | AUTO 分区显示 tuner 当前生效档位与最近调整原因（`model.config.get` 已有通道，扩展响应字段即可） |

## 4. 验证方案：性能提升不以质量为代价

### 4.1 性能指标（全部自动采集，进入 `InferenceTelemetry`）

| 指标 | 定义 | 采集方式 |
|---|---|---|
| TTFT | 请求起点 → 首个文本 delta | 分段计时 |
| TPOT / decode tok/s | 生成期均摊每 token 时间 | 分段计时 |
| prefill tok/s | promptTokens ÷ prefill 耗时 | 分段计时 + usage |
| KV 复用命中率 | CachedInputTokens ÷ promptTokens | 已有字段 |
| 显存峰值/常驻 | 权重+KV+workspace | 加载期日志解析 + 可选 NVML |
| 降级/OOM 率 | CPU 降级、DecodeError 次数 ÷ 总请求 | LoadReport + 异常计数 |
| 加载时长 | LoadDurationMs | 已有 |

### 4.2 输出质量指标（性能实验的并列验收项）

| 指标 | 工具/方法 | 检测什么 |
|---|---|---|
| 困惑度（PPL） | llama.cpp `perplexity` 工具 + wikitext-2 测试集 | KV 量化/FA 对模型分布的全局影响 |
| KL 散度 | 固定 prompt 下优化前后 logits 采样分布对比（温度 0） | 逐 token 分布漂移，比 PPL 更灵敏 |
| 确定性回归 | 固定 seed + 温度 0，对比优化前后输出文本 | 采样管线改动（S8）的正确性 |
| 任务准确率 | 固定评测集：代码生成（单测通过率）、摘要（ROUGE-L）、指令跟随（关键要素命中） | 端到端任务能力 |
| 长上下文召回 | 大海捞针（needle-in-haystack）抽点测试 | KV 量化 + 大 context 组合不丢信息 |

### 4.3 对比实验设计

1. **基准集**：四类 prompt 档案 × 每类 20 条——短问句（<512 tok）、中等任务（512~2k）、RAG 长上下文（8k~16k）、agent 多轮（复用命中率敏感）。固定 temperature=0 与固定 seed 各跑一遍（分别测质量与吞吐）。
2. **模型矩阵**：1.5B(Q4) / 7~8B(Q4、Q8) / 14B(Q4) × 上下文 4k / 16k / 32k；硬件固定（3070 Ti 8GB + 32GB 内存），另加一台核显机器验证 CPU 兜底档。
3. **单变量原则**：每个优化项（S1~S4 逐项）独立开关跑完整基准集，每配置 ≥5 次取中位数与 P90；记录 GPU 驱动、llama.cpp 版本、GGUF 文件 hash 进 manifest。
4. **验收门槛（双重）**：
   - 性能：TTFT 或 decode tok/s 相对基线提升 ≥15%（主策略目标：中型模型 32k 上下文下 TTFT −40%、decode ≥25 tok/s）；
   - 质量：PPL 劣化 <1%、KL 散度 <0.01、任务准确率掉幅 <2pp、针召回无新增空洞——任一超线即回退该项或收窄其启用条件。
5. **自适应机制专项**：固定一天真实使用分布的回放流量，对比"自适应" vs "固定最优人工配置" vs "当前默认"，衡量三者的 P50/P95 TTFT、降级率与重载次数（重载次数应 ≤ 人工配置且 P95 不劣于固定最优的 110%——这是自适应容忍的代价）。
6. **自动化**：新增 `benchmark` daemon 命令（或独立控制台工程）输出 JSON 报告，接入现有契约快照流程，保证优化不回归可持续度量。
