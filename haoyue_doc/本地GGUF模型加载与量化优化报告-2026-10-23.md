# 本地 GGUF 模型加载与量化优化报告（2026-10-23）

## 1. 目标与范围

对本机本地推理链路做两项优化并量化对比：

1. **模型加载优化**：mmap、层卸载（CPU/GPU 分配）、KV 缓存配置对启动速度与内存/显存占用的影响；
2. **量化优化**：在 Q4_K_M / Q5_K_M / Q8_0 之间按体积、速度、质量做权衡决策，并执行量化转换。

所有性能数字均走生产同一条链路（`LocalLlmClient` + `LocalModelCache` + llama.cpp CUDA 后端），
由新增基准工程 `benchmarks/model-opt/` 实测产出（用法见 §7）。

## 3. 优化方案与参数依据

### 3.1 模型加载优化

**现状**：加载链路已具备 mmap（`UseMemorymap` 默认开启， llama.cpp 日志中的
`CPU_Mapped model buffer` 即证据）、自适应装载档位（显存预算 → L1~L5 梯子）、
KV 量化（q8_0/q4_0）与 MoE 专家 CPU 卸载。gemma 冷加载 2.8~3.5s、显存峰值 4.6GB，
加载侧没有明显浪费。真正的问题有两处：

**问题 A：hybrid 架构 KV 估算虚高，档位误降（代码缺陷）**

`GgufProbe` 只解析标量 `*.attention.head_count_kv`。nemotron_h 等 hybrid 架构的该字段是
**逐层数组**（Mamba 层记 0），解析失败后回落到 `embedding_length/2`，KV 宽度被估成 1568
（实际注意力层为 1024），层数按 42 全量计算——32k 上下文的 KV 需求被估成约 8.6GB，
档位决策从「KV 驻显存」一路误降到 **tier3（KV q4_0 有损量化）**。

修复（`GgufProbe.cs` + `AdaptiveInferenceTuner.cs` + `LocalLlmClient.BuildShape`）：
- `GgufProbe.Header` 新增逐层 KV 头数组解析，`ModelShape` 新增 `KvLayers`（真实注意力层数）；
- KV 估算改为 `2 × KvLayers × KvDim × ctx × 2`；
- 新增 3 个回归用例（数组解析、hybrid KV 层数、档位结论），`AdaptiveInferenceTests` 42 例全过。

nemotron 的 KV 估算从 ~8.6GB 降到 512MB（4 层 × 1024 宽），档位回到 **tier1（f16 KV 无损）**。

**问题 B：nemotron（haoyue provider）关闭了 FlashAttention**

FA 是 KV 量化的硬性前提，且直接决定注意力核的显存带宽。该 provider 配置
`flashAttention: false`，导致非 FA 路径分配约 2GB 额外计算缓冲、长上下文 decode 与
prefill 双输。已改为 `true`。

**顺手清理**：删除悬空 provider「浩玥」（唯一模型文件不存在，加载必败），
顶层默认 provider/model 原本指向它，一并改指 google/gemma。
另：`DeepSeek-V4-Pro-Qwen3.5-9B-MTP-Q3_K_S.gguf` 经实测无法加载——文件声明 `qwen35`
架构但缺少 `blk.32.ssm_conv1d.weight` 张量（架构元数据与内容不匹配），任何 llama.cpp
构建均装不上（3 次尝试含 CPU 降级全败），已从配置移除，建议修复或删除该文件。

### 3.2 量化优化

**硬件约束**：8GB 显存下，gemma 权重 5.1GB + 32k 上下文 f16 KV 约 1.8GB（实际
SWA 结构约 1.3GB）+ 计算缓冲 0.5GB 已接近上限。Q8_0（7.6GB 权重）即便能装下，
decode 是显存带宽瓶颈型负载，权重每胖 50% 就要付约 20%+ 的速度税。

**方案权衡**（依据 llama.cpp 量化设计与本机实测）：

| 方案 | 体积 | 速度 | 质量 | 8GB 卡结论 |
|---|---|---|---|---|
| Q4_K_M | 5073 MiB | 基准 | 基线 | ✅ 舒适（峰值 4.6GB） |
| Q5_K_M | 5481 MiB（+8%） | 实测无损失 | 见 §5.3 | ✅ 可装（峰值 4.8GB） |
| Q8_0 | 7644 MiB（+51%） | 长上下文 -21%，且有病态慢路径 | 接近无损 | ❌ 峰值 6.0-6.4GB 且不稳定 |

**决策**：执行 Q5_K_M 与 Q8_0 转换做实证；Q8_0 因实测不可用在用户要求下取消
（文件已删除、配置已移除）。**量化源是本地 Q4_K_M 文件本身**（HF 网络不可达，
无全精度源可用），使用 `llama-quantize --allow-requantize --leave-output-tensor`，
输出层保留原精度以弥补 requantize 的二次损失——这一点决定了 §5.3 的质量结论。

## 4. 执行的操作

1. **代码修复**：`GgufProbe.cs`（逐层 KV 头数组）、`AdaptiveInferenceTuner.cs`（`ModelShape.KvLayers`）、
   `LocalLlmClient.cs`（`BuildShape` 按真实注意力层数估算）、`AdaptiveInferenceTests.cs`（+3 用例）；
2. **配置优化**（`~/.haoyue/config.json`）：haoyue provider `flashAttention → true`；删除悬空
   provider「浩玥」并修正顶层默认；注册 gemma Q5_K_M；
3. **量化转换**：llama.cpp b11819 自建 `llama-quantize`（MSVC+Ninja，CPU 后端）执行
   Q4_K_M → Q5_K_M（5480.85 MiB，49s）；Q8_0 已按要求取消并删除；
4. **基准工具**：新增 `benchmarks/model-opt/`（bench / quality / compare 三种模式，
   单模型失败不中断，透传 llama.cpp 原生日志）；
5. 实测修复过程中还定位并修复了基准工程自身的一个死锁（详见 §8）。

## 5. 优化前后性能对比

> 测量口径：冷加载 = 权重加载 + 512 自检；decode = 净解码速率（中提示约 30 token /
> 长上下文约 835 token 预填充）；RAM/VRAM = 进程/显卡峰值。同轮对比误差约 ±5%。

### 5.1 代码修复：nemotron（google provider，自动档位）

| 指标 | 旧代码（KV q4_0） | 新代码（KV f16） | Δ |
|---|---|---|---|
| 装载档位 | tier3，KV q4_0，272MB | tier1，KV f16，512MB | KV 无损化 |
| decode（中提示） | 99.3 tok/s | 121.0 tok/s | **+21.8%** |
| decode（长上下文） | 53.2 tok/s | 57.7 tok/s | **+8.5%** |
| prefill | 3001 tok/s | 3260 tok/s | **+8.6%** |
| 显存峰值 | 2966 MiB | 3087 MiB | +4.1% |
| 内存峰值 | 3800 MiB | 4297 MiB | +13.1% |

q4_0 KV 每次注意力读取都要反量化，在本卡上省下的带宽抵不上反量化开销——
f16 KV 同时更快且无质量损失，仅多占 240MB 显存。

### 5.2 配置优化：nemotron（haoyue provider，FlashAttention 开/关）

| 指标 | before（FA 关） | after（FA 开） | Δ |
|---|---|---|---|
| decode（中提示） | 109.9 tok/s | 108.9 tok/s | -0.9% |
| decode（长上下文） | 37.2 tok/s | 53.9 tok/s | **+45.0%** |
| prefill | 1481 tok/s | 3055 tok/s | **+106.2%** |
| 内存峰值 | 7141 MiB | 4485 MiB | **-37.2%** |
| 显存峰值 | 5341 MiB | 3318 MiB | **-37.9%** |
| 冷加载 | 1805 ms | 1828 ms | +1.3% |

### 5.3 量化对比：gemma-4-E4B（同轮干净环境实测）

| 指标 | Q4_K_M | Q5_K_M | Δ |
|---|---|---|---|
| 文件体积 | 5073 MiB | 5481 MiB | +8.0% |
| 冷加载 | 3135 ms | 2831 ms | -9.7%（噪声） |
| 内存峰值 | 5847 MiB | 6284 MiB | +7.5% |
| 显存峰值 | 4622 MiB | 4799 MiB | +3.8% |
| decode（中提示） | 71.8 tok/s | 71.6 tok/s | -0.3% |
| decode（长上下文） | 44.6 tok/s | 45.7 tok/s | +2.5% |
| prefill | 3547 tok/s | 3433 tok/s | -3.2% |
| 困惑度 PPL（12288 token） | 164.1 ± 11.1 | 166.7 ± 11.4 | +1.6%（误差内） |
| 问答质量（6 题贪心） | 基准 | 1 题完全一致；其余 64~72% 同主题；数学题均答对 | 无回归 |

**关键结论：从 Q4_K_M requantize 到 Q5_K_M 买不到质量。** 困惑度差异（+1.6%）完全在
误差棒内，问答输出等价。原因是信息在第一次 Q4 量化时已丢失，requantize 无法恢复，
只能改变位宽表示。Q5_K_M 的理论优势只在**从 F16/BF16 全精度源量化**时成立。

### 5.4 Q8_0（已取消）

| 指标 | 数值 |
|---|---|
| 体积 | 7644 MiB（较 Q4 +50.7%） |
| 显存峰值 | 6034~6427 MiB（+31~39%） |
| decode（长上下文） | 35.3~35.7 tok/s（**-21~22%**） |
| 稳定性 | 观测到病态慢路径：短/中提示生成仅 0.3~0.7 tok/s 且 GPU 100% 满载；同配置换轮次为 28~55 tok/s，不稳定 |

8GB 卡上 Q8_0 既慢又挤占显存，交互场景不可用。文件（7.5GB）已删除，配置条目已移除。

### 5.5 其他观测

- **gpt-oss-20b**：decode 仅 10.9~12.7 tok/s——`moeExpertsOnCpu: true` 把专家权重留在
  CPU（10949 MiB CPU_Mapped），每步都要过 PCIe。要提速需关闭专家 CPU 卸载（显存不够）
  或缩小上下文，属配置权衡而非缺陷。
- **qwen2.5-0.5b**：decode 268~284 tok/s、冷加载 1.5s，小模型无优化空间。
- **gemma 加载**：mmap 默认开启，43/43 层卸载 GPU，输出层留 CPU（CPU_Mapped 2730MB），
  冷加载 2.8~3.5s；KV q8_0 + FA 已是合理配置。

## 6. 结论与建议

1. **gemma 默认档保持 Q4_K_M**。本地无全精度源，requantize 到 Q5_K_M 只有 +8% 体积、
   零可测质量收益；Q8_0 在 8GB 卡上不可用。若未来网络恢复，应从 HF 拉 gemma-4-E4B 的
   BF16 源重新量化 Q5_K_M/Q6_K，那时的对比才有意义（Q5_K_M 文件已就位可作对照）。
2. **所有本地 provider 保持 FlashAttention 开启**（本次为 nemotron 开启，长上下文
   decode +45%、prefill +106%、内存/显存各 -37%）。
3. **hybrid 架构 KV 估算修复已生效**：nemotron 档位 tier3→tier1，decode +22% 且 KV
   不再有 q4_0 量化损失。新增 hybrid 模型家族时确认 `head_count_kv` 数组解析覆盖。
4. **修复或删除损坏的 DeepSeek-V4-Pro-Qwen3.5-9B-MTP-Q3_K_S.gguf**（缺 SSM 张量，
  任何 llama.cpp 都无法加载）；已从配置移除。
5. **gpt-oss-20b 若要交互使用**：评估显存预算后尝试 `moeExpertsOnCpu: false`，
   或把 contextWindow 从 32768 调低；当前 CPU 专家路径只有 ~11 tok/s。

## 7. 复现方法

```bash
# 基准（NVIDIA 机器必须带 Cuda12 后端）
dotnet run --project benchmarks/model-opt/haoyue_model_opt.csproj -c Release \
  -p:LlamaBackend=Cuda12 -- bench --tag <tag> [--filter 子串] [--threads N]

# 质量对比（固定题本 + 贪心 + 种子 42）
dotnet run ... -- quality --tag <tag> --filter gemma
dotnet run ... -- compare <a.json> <b.json>

# 困惑度（CPU）
llama-perplexity -m <model.gguf> -f <corpus.txt> -c 2048 --chunks 10 -t 16
```

结果写入 `benchmarks/model-opt/results/`（bench-*.json、quality/*.json）。

## 8. 过程备注：基准工程死锁（已修复）

首轮基准挂死 15 分钟无任何输出。定位：`LocalModelCache.MaxConcurrency` 默认 1
（配置 `localModelConcurrency: 1`），推理槽是一把单信号量；基准为测冷加载先持有
lease，再调 `StreamAsync`（内部再 Acquire 同一把槽）构成嵌套获取，自死锁
（证据：无第二次 context 创建日志、CPU/GPU 全静默、GPU 空转）。修法：冷加载度量
用完立即释放 lease，权重不卸载、后续生成仍命中同一槽位。修复后同基准全链路跑通。
此为基准工程用法问题，runtime 无需改动——daemon 每次请求只 Acquire 一次，不构成嵌套。
