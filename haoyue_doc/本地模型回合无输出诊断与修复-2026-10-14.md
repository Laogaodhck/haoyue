# 本地模型回合无输出诊断与修复

- 日期：2026-10-14
- 范围：`haoyue_runtime/Daemon`、`haoyue_runtime/Providers`、`haoyue_desktop`（主进程与渲染层）、`haoyue_cli/Ui`
- 现象：桌面端发消息没有回复；首条消息要等一两分钟且界面毫无反馈；Runtime 偶发无征兆退出后被自动重启
- 状态：✅ 已实施（1.3.25 加载进度与固化让路、1.3.26 广播副本修复，打包版实测通过）

---

## 0. 为什么这类问题原本无法诊断

daemon 是 Electron 主进程 spawn 的子进程，其 stdout/stderr 原先只进不出：既不落盘，也没有控制台。Runtime 崩溃时用户侧只剩「没有回复」，维护侧没有任何栈、退出码或原生层输出可查。

因此第一步不是猜根因，而是先补观测通道：`haoyue_desktop/src/main/daemon-log.ts` 把子进程全部输出写入 `<userData>/logs/daemon.log`（8 MiB 轮转到 `daemon.prev.log`），每次 spawn 写一行分隔标记，进程退出时写 `----- daemon exit code=… signal=… -----`；重启次数耗尽后的桌面通知附带最后一行 stderr 与日志路径。

```
===== daemon spawn 2026-10-14T11:08:30.611Z =====
llama_new_context_with_model: ... （此前被丢弃的原生输出）
Unhandled exception: System.InvalidOperationException: The node already has a parent.
   at System.Text.Json.Nodes.JsonObject.SetItem(String propertyName, JsonNode value)
   at Haoyue.Runtime.Daemon.DaemonServer.WriteAsync(...)
   at Haoyue.Runtime.Daemon.DaemonServer.BroadcastAsync(...)
   at Haoyue.Runtime.Daemon.DaemonServer.BroadcastHostEventsAsync(...)
   at Haoyue.Runtime.Daemon.DaemonServer.DisposeAsync()
----- daemon exit code=1 signal=none -----
```

正是这个文件在补上后的第一次验证中直接给出了第三个根因的完整栈。

## 1. 根因一：后台记忆固化与用户回合抢显存

- 机制：H-C 记忆固化（daemon 启动时 + 每 6 小时）在隔离运行时里跑一个完整 agent 回合，用的是同一个共享 `LocalModelCache`。用户回合正在飞行时，两份约 5 GB 的 GGUF 权重同时驻留，8 GB 显存的 RTX 3070 Ti 装不下，llama.cpp 在原生层直接 abort——原生 abort 不经过托管异常，没有任何终态事件发给客户端，连接就这么断了。
- 修复：`DaemonServer.StartConsolidation` 在 `_sessionTurns.Count > 0` 时不再启动固化，改为设一个 2 分钟的一次性定时器重排；定时器对象常驻但不会重复排队，多次让路合并成一次重试。
- 边界：这是时间让路，不是显存配额调度。同一时刻仍只保证「固化不与用户回合并发」，两个并发用户回合各自加载不同权重的场景不在本次收敛范围内（`LocalModelCache` 的槽位与 LRU 另有约束）。固化让路目前是私有方法 + 定时器，没有单元测试覆盖，仅由打包版行为观察确认。

## 2. 根因二：冷加载一两分钟没有任何客户端可见进度

- 机制：本地权重冷加载实测约 152 秒。`model.preload` 这条管理路径传了 `IProgress`，而真正的对话回合走 `LocalModelCache.AcquireAsync` 的 `progress: null` 重载，于是加载期间客户端一个事件都收不到，界面看起来与卡死无异。
- 修复：在缓存层加旁路事件，进度不再依赖调用方是否传回调。
  - `LocalModelCache.LoadProgressObserved`：任何一次权重加载（含回合内懒加载）都会上报，终态 `Failed` 同样上报，否则客户端进度会永远停在最后一个阶段。
  - daemon 订阅该事件，桥接成 `ModelLoadProgressEvent` 并广播新契约事件 `model.load.progress`（`details` 含 `model` / `phase` / `percent` / `elapsedMs` / `estimatedRemainingMs` / `message`）。
  - runtime 自带的缓存在 DI 工厂里把同一事件发到进程内 `IEventBus`——CLI 这类进程内宿主没有 daemon 桥接，靠这条路径拿到进度。
  - CLI `TerminalRenderer` 状态行显示「Loading model N%」→ Ready 转「Thinking」→ Failed 转「Model load failed」；桌面渲染层把阶段翻译成「加载本地模型 N%」「思考中」「本地模型加载失败」。
- 验证：`LoadProgressObserved_FiresWithoutCallerProgress`、`RuntimeOwnedCache_PublishesProgressOnItsEventBus` 两个用例分别覆盖旁路事件与进程内总线；`model.load.progress` 已进入契约快照与生成的 TS 联合类型（未声明的广播名会直接编译报错）。

## 3. 根因三：多客户端广播把同一个 JsonNode 挂了两遍

- 机制：`JsonNode` 只允许一个父节点。`BroadcastAsync` 把同一个 `details` 引用依次挂给每个连接的信封，第一个连接成功，第二个连接在 `JsonObject.SetItem` 抛 `InvalidOperationException: The node already has a parent`。该异常沿事件泵 `BroadcastHostEventsAsync` 冒泡，在 `DisposeAsync` 处重掀掉整个 daemon——托管侧表现为进程退出码 1，用户侧表现为「发消息没有回复」。
- 影响面：所有带 `details` 的广播（`task.updated`、`mcp.updated`、`schedule.updated` / `schedule.upcoming`、`evolution.reflected`、`memory.consolidated`、`turn.interrupted`、`model.load.progress`），且只在 ≥2 个客户端同时连接时触发——桌面端与 CLI 同开、或桌面端开两个窗口即命中。单客户端下永远复现不出来，这也是它潜藏至今的原因。
- 修复：`WriteAsync` 写入前 `details.DeepClone()`，每个连接各拿一份副本；广播循环额外兜住非断连异常，只写一行 `Daemon broadcast failed (<event>): <message>` 到 stderr，绝不让单个客户端掀掉事件泵。
- 验证：`Broadcast_WithDetails_ReachesEveryConnectedClient` 在同一 daemon 上开两条管道连接，断言两边都收到 `task.updated` 的 `details`。反证有效——把 `DeepClone()` 还原成直接引用后，第二个连接永远等不到广播，用例在 30 秒读超时上失败。

## 6. 后续候选

- 显存配额调度：让固化与用户回合竞争的是预算而非时间窗（`LocalModelCache` 已有槽位与 LRU，缺按 VRAM 的准入判定）。
- 大 `details` 广播的流式序列化：当前每连接一次 `DeepClone` + `ToJsonString`，事件体积大时可在信封层做一次序列化后按连接复用字符串。
- 崩溃可观测性：把原生 abort 这类不经托管异常的死法与托管退出码区分开（当前只能靠 `exit code` 与日志尾部推断）。
