# 状态并发、上下文边界与原子性风险评审

- 日期：2026-10-07
- 范围：针对三项架构疑虑（State Hell / Context Overload / Action Transactionality）逐项对照当前代码核实，给出风险分级与实施方案。
- 结论先行：**三项痛点部分成立**。会话存储已是 SQLite（WAL），"JSONL 并发写"不成立；真实风险集中在①config.json 跨进程丢失更新、②系统提示总量无上限、③文件工具非原子写 + 崩溃不一致窗口。全工作流 Saga 不建议照搬，理由见第三节。

---

## 一、痛点 1：状态管理与并发性（State Hell）

### 1.1 现状核实

| 存储 | 写入者 | 写入方式 | 跨进程保护 |
|---|---|---|---|
| `~/.haoyue/haoyue.db`（会话/消息/事件/任务/知识） | CLI 与 daemon 都直连 | SQLite WAL + busy_timeout=10000 + 单消息事务 | ✅ 唯一有跨进程保护 |
| `~/.haoyue/config.json` | **CLI 与 daemon 都整文件覆盖写** | `File.WriteAllText`，非原子，进程内锁仅实例级 | ❌ 无 |
| `~/.haoyue/state.json`（技能开关） | CLI 与 daemon 都写 | 同上 | ❌ 无 |
| `~/.haoyue/usage.jsonl` | 两进程各自 UsageTracker | `File.AppendAllText`，进程内静态锁 | ❌ 无 |
| `~/.haoyue/active-turns.json` | 仅 daemon | temp+rename 原子写（全仓唯一原子写范式） | 仅进程内 |
| 会话 JSONL | **已无人写**，仅遗留导入（SessionStore.cs:609） | 只读/删除 | — |

进程内并发防护已相当完整：`FileLockCoordinator`（per-file SemaphoreSlim 守工作区源文件）、per-session 回合互斥（`_sessionTurns`）、`_adminGate` 串行化管理操作、`SessionGates`/事务保会话写入。

### 1.2 风险分级

- **S1（高）config.json 跨进程丢失更新**：用户同时开 `haoyue chat` 与 daemon/Desktop，CLI `/mode`（ChatLoop.cs:308）与 daemon `SaveMode`（DaemonServer.cs:1677）各持内存快照互相覆盖；非原子写还可能被读到半截 JSON（损坏兜底 `.corrupt.*.bak` 存在，但数据已丢）。
- **S2（中）ActiveTurnJournal 固定 `.tmp` 文件名**：daemon 多连接并发回合同时 `Write` 会互踩同一个临时文件（ActiveTurnJournal.cs:32-34），异常被 best-effort catch 吞掉 → 崩溃恢复偶发漏一条记录。
- **S3（低）usage.jsonl 长行交错**：两进程并发 Append 无保护；统计文件，容忍度高。

### 1.3 实施方案

| 编号 | 方案 | 梯队 |
|---|---|---|
| A1 | `ConfigStore.Save` 改 temp+rename 原子写（复用 ActiveTurnJournal 范式），state.json 同 | 第一梯队 |
| A2 | ConfigStore 写前 reload-merge：保存时从磁盘重读最新配置、按字段合并内存改动后写回，消除丢失更新 | 第一梯队 |
| A3 | ActiveTurnJournal 临时文件名加 `Guid` 后缀（`path + "." + Guid.NewGuid() + ".tmp"`） | 第一梯队（一行改动） |
| A4 | 全局 config 写操作收敛到 daemon：CLI 管理命令改走 daemon RPC（架构级根治"多写者"→"单写者"），CLI 未连 daemon 时保持现状并提示 | 第二梯队（涉及 CLI 命令面，单独评估） |

## 二、痛点 2：提示词与上下文边界（Context Overload）

### 2.1 现状核实

注入层次清晰（PromptSlot：System→Developer→Workspace→Skill→Tool→Memory，PromptRegistry.cs:4-12），信任包装矩阵已基本落位：

- **已包装**（EXTERNAL CONTENT 数据非指令）：MCP prompt/resource、技能 SKILL.md/prompt.txt 正文。
- **未包装**：AGENTS.md（仅 Fit 截断，靠模板弱信任措辞）、MCP 工具描述与 schema（原样透传，行业灰色地带）。
- **优先级仲裁**：无结构化机制，仅 system/default.txt 内"Trust boundaries"等自我声明，靠模型自行判断。

### 2.2 风险分级

- **C1（高）系统提示总量无上限**：`MaxSystemPromptTokens = 24_000`（ContextPlanner.cs:27）**定义了但全仓库无任何调用点强制执行**。单片段有 `MaxInjectedFragmentTokens = 10_000` 顶，但片段数量无上限——N 个 always-on 技能 × 10k + M 个 MCP prompt × 10k + AGENTS.md 10k，理论最坏 60k-100k+ token，直接挤压对话历史预算（WindowBudget 扣减后余量枯竭），且不截断不告警。
- **C2（中）AGENTS.md 未信任包装**：工作区文件可被第三方依赖改写，是提示注入的现实入口（现状仅靠 agents_md.txt 模板措辞）。
- **C3（中）MCP prompt 无数量上限**：resource 有 `MaxResourcesPerServer`，prompt 没有对应限额。
- **C4（低）死模板**：`builtin/context.txt` 无任何代码引用。

### 2.3 实施方案

| 编号 | 方案 | 梯队 |
|---|---|---|
| B1 | PromptComposer 组装完成后强制执行系统提示总预算（24k）：超限时按槽位**逆序降级**——先丢 Memory 槽附加层（computer/knowledge），再丢 Skill 正文（保留技能目录，模型可 declare_skill 按需加载），再丢 MCP prompt/resource，System/Developer 槽永不丢弃；降级发生时在提示尾部注入一条运行时通知说明哪些层被省略。这是"结构化优先级仲裁"的代码级落地，且与 N5 declare_skill 机制天然衔接 | 第一梯队 |
| B2 | AGENTS.md 内容套 `WrapUntrustedSource`，agents_md.txt 模板措辞同步调整（user-authored 但非运行时权威） | 第一梯队（小改动） |
| B3 | MCP prompt 增加 per-server 数量/总量限额（复用 MaxResourcesPerServer 思路） | 第二梯队 |
| B4 | 删除 builtin/context.txt 死模板 | 第一梯队（顺手） |

> 指令冲突本身（技能正文描述与工具 schema 不一致）无法代码消除——技能正文已是不可信数据包装，模型按"Trust boundaries"约定处理即为行业现状；B1 的总量控制把冲突概率随上下文膨胀一起压下来。

## 三、痛点 3：动作原子性（Transactionality）

### 3.1 现状核实

- **并发层有**：变异工具经 `WithFileWriteLockAsync` 中央写锁 + 锁内重读（FileTools.cs:54-83）；会话写入单消息事务。
- **单操作层无**：`write_file`/`edit_file` 都是 `File.WriteAllTextAsync` 直写（FileTools.cs:185/244），无 temp+rename、无备份——取消或 IO 异常可留**半截文件**。
- **失败恢复层几乎没有**：全仓无 undo/rollback/补偿。崩溃仅靠 ActiveTurnJournal 标记"turn 死了"，重启后只补中断提示、明确不重跑（DaemonServer.cs:1604 注释：半执行工具使盲目重试不安全）。
- **不一致窗口**：工具副作用生效（Agent.Tools.cs:69）→ `sessionStore.Append`（Agent.cs:126）之间崩溃，文件已改而会话无记录，无对账。
- **外部副作用**：shell 取消只 kill 直接子进程无进程组（孙进程可存活）；MCP 60s 超时无重试（重试由 LLM 下一轮决定，归属清晰）。

### 3.2 关于"Saga 模式"的裁决

**不建议做全工作流 All-or-Nothing。** 理由：

1. Agent 的步骤序列由 LLM 动态决定，边界在运行前不可知，Saga 需要的确定性事务边界不存在。
2. 工具副作用是任意外部系统（shell 命令、MCP 服务器），系统既无能力也无权限为它们构造补偿动作——强做只会给出虚假安全感。
3. 崩溃恢复"不自动重跑"是正确设计，与半执行工具的现实一致。

**正确路线：受控子集做原子写与可撤销，外部副作用做记录与对账提示。**

### 3.3 实施方案

| 编号 | 方案 | 梯队 |
|---|---|---|
| T1 | `write_file`/`edit_file` 改 temp+rename 原子写（同目录 temp，先写后 `File.Move(overwrite:true)`），消除半截文件；锁内已有重读逻辑不动 | 第一梯队 |
| T2 | Turn 级文件变更账本：turn 内 write/edit 成功前把旧内容记入内存 journal（上限如 50 文件/20MB，超限降级为只记录路径）；turn 失败/取消时广播"本 turn 修改了 N 个文件，可撤销"，用户确认后按账本逆序恢复旧内容。**仅覆盖内建文件工具，shell/MCP 明确声明不覆盖** | 第二梯队 |
| T3 | 崩溃对账：ActiveTurnJournal 的 ActiveTurnRecord 增记本 turn 已变异文件路径清单；恢复时（RecoverInterruptedTurnsAsync）把清单列入中断提示，提示用户检查这些文件与会话记录的差异。只提示、不自动回滚（与现有"不盲目重试"原则一致） | 第二梯队 |
| T4 | shell 进程组终止（Windows Job Object / POSIX process group） | 第三梯队/观察项（成本高收益有限） |
| T5 | MCP 重试保持 LLM 驱动（现状合理），不做框架级自动重试 | 不实施（裁决） |

## 四、汇总与建议顺序

**第一梯队（建议立即实施，共 7 项）**：A1 原子写 config/state → A2 写前合并防丢失更新 → A3 journal 临时文件名随机化 → B1 系统提示总预算+槽位降级 → B2 AGENTS.md 信任包装 → B4 死模板清理 → T1 文件工具原子写。

**第二梯队**：A4 config 单写者收敛、B3 MCP prompt 限额、T2 turn 级撤销、T3 崩溃对账清单。

**第三梯队/裁决不做**：T4 进程组终止（观察）、T5 MCP 自动重试（不做）、全工作流 Saga（不做，理由见 3.2）。

**已核实不成立的担忧**：会话 JSONL 并发写（已迁 SQLite/WAL，逐行容错加载）；haoyue.db 跨进程并发（WAL + busy_timeout 已覆盖）。

预期效果：第一梯队落地后，"State Hell"收窄为单点（A4 的 CLI 收敛可后续根治）；上下文膨胀从"静默失控"变为"有预算、有降级、有告知"；文件工具从"可留半成品"变为"单操作原子"，配合 T2/T3 形成受控子集的撤销与对账能力，而不引入虚假的全局原子性承诺。
