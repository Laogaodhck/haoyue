# MCP 连接体验优化方案（开箱即用化）

日期：2026-10-08
范围：haoyue_runtime/Mcp、haoyue_desktop（MCP 设置页）、haoyue_cli、haoyue_doc
目标：把「填 7~9 个字段才能连上一个 MCP 服务器」压缩到「粘贴一个包名/URL + 最多补一个凭证」，同时保持与现有 MCP 服务器和既有 JSON 配置的完全兼容。

---

## 一、现状盘点

### 1.1 当前一次连接需要提供的参数

| 参数 | 必填性 | 当前来源 | 说明 |
|---|---|---|---|
| name | 必填 | 用户手填 | 工具名前缀 `mcp__<name>__`，也是配置键 |
| scope | 必填 | 用户选 workspace/global | 决定写入哪个配置文件 |
| transport | 必填 | 用户选 stdio/SSE/HTTP | `McpServerConfig.Transport`，默认 stdio |
| command + args | stdio 必填 | 用户手填 | 两行文本框，逐行拆分 |
| env | stdio 可选 | 用户手填 `KEY=value` | 凭证目前也放这里（明文落盘） |
| url | 远程必填 | 用户手填 | 必须 http(s):// 开头 |
| enabled | 可选 | 默认 true | — |
| MutatingTools / ReadOnlyTools / TrustReadOnly | 高级 | 几乎无人填 | 变更类工具判定（fail-closed 已是安全默认） |

传输与超时为内部固定值：远程连接 ConnectTimeout 10s、初始化 30s（`McpManager.ConnectOneAsync`），对用户不可见也不可调——这本身是合理的默认，问题只在**用户可见的必填字段太多**。

### 1.2 现有能力基础（可直接复用）

- **预设模板**：桌面端 `mcp-form.ts` 已有 GitHub / 文件系统 / fetch / memory / sequential-thinking / git 六个预设，自动填 command/args/env 键名；GitHub 还带 token 申请直达链接。
- **后台重连**：`mcp.upsert` 保存即返回，连接后台进行 + `mcp.updated` 广播，单服务器失败不拖垮整体。
- **凭证不回显**：`mcp.list` 只返回 env 键名，UI 编辑时需重填值。
- **CLI 自检**：`haoyue mcp list / test`。

### 1.3 主要缺口

1. **无 HTTP headers / 认证字段**：`HttpMcpTransport` 只接收 url，远程服务器要求的 `Authorization: Bearer …` 完全无法配置（`HaoyueConfig.McpServerConfig` 无 `Headers` 字段）。这是「开箱即用」的硬缺口，不是体验问题。
2. **凭证明文落盘**：env 值直接写 `~/.haoyue/config.json`。
3. **transport/command/args/url 四个字段的判断全部推给用户**，而其中 90% 的信息可以从用户粘贴的内容中推断。
4. **name、scope 也推给用户**，均可推断或给默认。

## 二、逐项评估：自动填充 / 隐藏 / 智能推断 / 合并默认值

判断依据统一为三条：
- **依据 A（可推断性）**：该参数是否能从用户必然提供的另一项信息中高置信度推出（歧义率 < 5%）。
- **依据 B（错误代价）**：推断错误的可发现性与修复成本。连接测试秒级可发现 → 允许激进推断；静默错误（如安全语义）→ 不推断。
- **依据 C（兼容性）**：改动是否只发生在「输入层」，存储 schema 保持向后兼容（旧字段仍合法）。

| 参数 | 处置 | 判断依据 |
|---|---|---|
| transport | **隐藏 + 智能推断**：输入以 `http(s)://` 开头 → `http`（Streamable HTTP，现行规范）；否则 → `stdio`。 | 依据 A/C。协议层面 Streamable HTTP 服务端对旧式 GET 探测已有 405 回退兼容（`HttpMcpTransport.StartAsync`），推断成 http 不会连不上 SSE-only 服务器；错误在连接测试立即可见（依据 B）。UI 上不再让用户理解三种传输的差别——这是豆包/WorkBuddy 不暴露该概念的根本原因：**transport 是实现细节，不是用户意图**。 |
| command + args | **合并为单行「启动命令」**（如 `npx -y @modelcontextprotocol/server-github`），系统做类 shell 分词（尊重引号）。**进一步省略解释器前缀**：输入以 `@` 开头或含 `/` 的包名 → 自动补 `npx -y`；输入 `mcp-server-*` → 自动补 `uvx`。预设模板仍保留一键填充。 | 依据 A：npm 包名与 uvx 包名命名约定高度可识别；依据 B：分词错误在连接测试可见。保留高级模式的双行编辑器作为兜底，兼容任意可执行文件路径。 |
| url | 必填无法消除，但支持**智能粘贴**：直接粘贴完整 JSON 配置片段（Claude/Cursor 的 `mcpServers` 格式）时自动解析出全部字段；粘贴 `mcp-remote` 风格 URL 同理。 | 生态兼容的关键入口——用户网上抄来的配置大多带完整 JSON，粘贴即用是「开箱即用」感知最强的一步。 |
| env | **凭证框化**：预设声明所需 env 键（现状已有），值改为密码输入框；保存时值不再明文落盘（见第四节安全设计）。 | 依据 B：凭证泄露是不可逆错误，必须从「顺手感」升级为「显式输入 + 加密存储」。 |
| name | **自动推断 + 可改**：stdio 从包名取尾段（`server-github` → `github`），远程从 URL 主机名取主体（`mcp.example.com` → `example`），冲突自动加后缀。 | 依据 A/B：name 错了只影响工具前缀美观度，无功能损失，且连接测试面板可见。 |
| scope | **默认全局**，高级模式可改工作区。 | 语义对齐 WorkBuddy/豆包连接器：用户心智里「接入 GitHub」是一次性的全局行为，不是每工作区重复的事。工作区覆写机制保持不变，只是默认值反转。 |
| enabled | 默认 true，**隐藏**。 | 依据 C：新添的服务器不启用反直觉；禁用走列表行的开关（现状已有）。 |
| 超时 | 保持内部默认（10s/30s），**高级模式可调**，新增可选字段 `connectTimeoutSeconds`。 | 依据 B：默认值已合理，暴露只会制造困惑；但内网慢服务器需要逃生门。 |
| MutatingTools / ReadOnlyTools / TrustReadOnly | 保留，**归入高级折叠区**。 | fail-closed 默认已是安全最优；这是安全语义参数，不做任何推断（依据 B）。 |
| HTTP headers | **新增字段**（不是隐藏）：远程服务器支持 `headers: { Authorization: "Bearer …" }`，值为 `secret:` 引用时走加密存储。 | 缺口补齐，见下节。 |

**净效果**：主路径用户可见输入从 7 项降到 **1 个粘贴框 +（仅当服务器需要时）1 个凭证框**；兜底高级模式保留全部字段，兼容性零损失。

## 三、简化后的参数设计与配置流程

### 3.1 存储schema（向后兼容扩展）

```jsonc
// ~/.haoyue/config.json → mcp.servers.<name>
{
  "transport": "stdio",              // 语义不变；UI 不再要求用户选择，由输入层推断写入
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "secret:dpapi:AQAA..." },  // 值可带 secret: 前缀
  "url": null,
  "headers": { "Authorization": "secret:dpapi:AQAA..." },             // 新增，仅远程传输读取
  "connectTimeoutSeconds": 10,                                         // 新增，可选
  "enabled": true
}
```

兼容性规则：
- `headers` / `connectTimeoutSeconds` 为新增可选字段，旧配置不含它们照常工作；`HttpMcpTransport` 构造函数增加 `IReadOnlyDictionary<string,string>? headers` 参数，请求时逐个 `TryAddWithoutValidation`。
- `secret:` 前缀值在 `StdioMcpTransport`/`HttpMcpTransport` 启动前由 `SecretResolver` 解密为真实值；不带前缀的值行为不变（明文，兼容旧配置）。
- 工作区三层合并顺序不变（全局 → `<ws>/.haoyue/mcp/servers.json` → `<ws>/.haoyue/config.json`）。

### 3.2 配置流程（一步式「添加连接」）

主界面仅一个输入框 + 一个「识别」动作，四步完成：

| 步骤 | 用户操作 | 系统行为 |
|---|---|---|
| ① 粘贴 | 在输入框粘贴任意一种：包名（`@modelcontextprotocol/server-github`）、完整启动命令（`npx -y …`）、URL（`https://mcp.example.com/mcp`）、完整 JSON 配置 | 「识别」实时分类：JSON → 解析全部字段；URL → transport=http、name=主机名；包名/命令 → 分词、补解释器前缀、name=包尾段。识别结果以只读摘要回显（"将启动本地命令 npx -y …" / "将连接 https://…"），点「高级」可展开改任何字段 |
| ② 补凭证（条件出现） | 若识别出预设已知凭证键（如 GitHub）或服务器带 `headers`/`env` 键，出现密码框 | 凭证框只显示键名与掩码；预设场景给出申请链接（复用 `githubTokenCreateUrl`）。用户可跳过——连接测试会以明确错误提示「缺少 GITHUB_PERSONAL_ACCESS_TOKEN」 |
| ③ 测试 | 点「测试连接」 | 后台执行单服务器 `ConnectOneAsync`（30s 上限），显示：连接成功 / 工具数 / 失败原因（复用 `DescribeConnectionError` 的中文化错误映射）。测试通过后凭证立即加密落盘 |
| ④ 完成 | 点「添加」 | 写入全局配置（默认 scope）→ 后台重连 → 列表行出现，状态由 `mcp.updated` 广播刷新。无任何额外确认步骤 |

已有服务器的编辑路径不变（列表行 → 编辑对话框），编辑时凭证框显示「已保存（留空则不修改）」，解决现状「编辑需重填全部 env」的痛点。

### 3.3 稳定性保障（复用 + 小改）

- 单服务器失败不中断整体加载：现状已有，保持。
- 连接测试超时 30s 上限：现状已有，保持。
- 新增：识别歧义时不静默猜测——粘贴内容既非 URL 也非可分词命令也非 JSON 时，降级为高级模式打开并提示「无法识别，请手动填写」。
- 新增：stdio 命令启动失败（如 npx 不存在）的 `Win32Exception` 错误文案补充「请确认已安装 Node.js/Python 工具链」指引（现状只给原始异常消息）。

## 四、凭证安全设计

| 环节 | 措施 |
|---|---|
| 存储 | Windows：DPAPI（`System.Security.Cryptography.ProtectedData`，CurrentUser 作用域，同用户进程可解、跨机器不可解）；Linux：优先 libsecret（Secret Service API），无桌面密钥环时退回 `~/.haoyue/secrets.json`（0600 + DPAPI 等价的 AES-GCM，密钥派生自机器标识并在文档中明示弱于 DPAPI）。加密产物以 `secret:dpapi:` / `secret:file:` 前缀内联在配置里，配置文件本身保持单文件可备份 |
| 传输 | 远程 MCP 一律要求 https 才允许携带 `headers` 凭证；`http://` + headers 组合在保存时警告（本地调试 `http://127.0.0.1` 豁免）。stdio 的 env 仅通过进程环境传递，不经命令行（现状已满足） |
| 回显 | 现状「mcp.list 只返回 env 键名」扩展到 headers：值永不回显，编辑留空=不修改 |
| 日志 | `mcp.updated`、连接错误信息中过滤 `secret:` 与 Authorization 值 |
| 进程内 | 解密后的凭证只在 Transport 实例内存中持有，不进任何缓存/序列化上下文（`HaoyueJsonContext` 不注册解密后类型） |

## 五、WorkBuddy 连接器移植可行性评估

### 5.1 结论先行

**完整移植不可行，也不应移植。** WorkBuddy 的「连接器开箱即用」由三层平台基础设施支撑，均不在 haoyue 的架构假设内：

1. **云端授权代理（OAuth broker）**：连接器 `bound` 状态由平台服务端管理，OAuth 授权、token 刷新、多设备同步全部发生在平台侧。haoyue 是本地优先运行时，没有也不应有常驻云端身份服务——引入它意味着 haoyue 的所有连接器流量都要经过一个中心化信任点，与项目隐私定位冲突。
2. **插件市场与分发体系**：连接器候选来自市场检索 + 一键安装卡。haoyue 的 MCP 生态是标准 MCP 协议，任何 MCP 服务器天然就是「候选」，缺的是发现入口而非分发通道。
3. **凭证集中托管**：平台替用户保管凭证。上一节的本地加密存储是更符合 haoyue 形态的替代。

### 5.2 值得移植的最小子集：本地 OAuth 授权助手

WorkBuddy 体验中**协议层可移植**的部分是：对声明 OAuth 2.0 授权的远程 MCP 服务器（MCP 2025-03-26 规范定义了 authorization 元数据），客户端自动发起授权码流程：

- 发现服务器 401 → 读取 `WWW-Authenticate` / `/.well-known/oauth-protected-resource` → 打开系统浏览器授权 → loopback 回调（`http://127.0.0.1:<ephemeral>`）接收 code → 换 token → 按 `secret:` 机制存储。
- 用户体验等价于 WorkBuddy 的「授权连接」：点一下、浏览器跳转、回来即连上。
- 改动面：`HttpMcpTransport` 增加 401 处理钩子 + 新增 `McpOAuthFlow` 类（约 300~400 行）+ token 刷新后台任务。风险：refresh token 过期后的重新授权交互、多服务器并发授权的回调端口管理、授权页在无默认浏览器环境的降级。

### 5.3 两方案对比

| 维度 | 方案 A：输入层简化 + 本地凭证加密（本方案） | 方案 B：移植 WorkBuddy 连接器体系 |
|---|---|---|
| 用户操作减少 | 7 项 → 1 粘贴 + ≤1 凭证 | 同级，另加市场发现入口 |
| 与现有 MCP 服务器兼容 | 100%（输入层改动，schema 向后兼容） | 需为非 OAuth 服务器保留整套旧路径，双轨并存 |
| 改动面 | `McpServerConfig` +`headers/secret`、`HttpMcpTransport` +headers、桌面 `mcp-form.ts`/`McpEditorDialog.vue` 重构输入区、`SecretResolver` 新类 | 除上述全部外，还需云端授权服务 + 市场后端 + 客户端插件框架，且引入中心化信任点 |
| 风险 | 低：预设/JSON 粘贴识别歧义（有降级路径）；DPAPI 在被入侵账户下可解（与 WorkBuddy 平台托管同级风险） | 高：基础设施成本、隐私定位冲突、OAuth 生态碎片化（各服务器元数据实现参差） |
| 见效周期 | 一期内可交付 | 数月级平台工程 |

### 5.4 推荐

**采用方案 A，并将 5.2 的本地 OAuth 授权助手作为二期可选项。** 理由：用户感知的「开箱即用」90% 来自「少填字段 + 粘贴即用 + 凭证只填一次」，这三点方案 A 全覆盖且零兼容代价；WorkBuddy 体验中剩下的 10%（市场发现、云端授权）依赖 haoyue 不具备且不应该自建的平台设施，其可移植精髓（MCP 规范内的 OAuth 流程）可以低成本单独吸收。

## 附：判断依据的边界声明

- 所有「智能推断」只发生在**输入层**，存储的配置永远是显式展开后的完整字段——用户随时可以在高级模式里看到并修正系统替他做的决定。这与「把推断藏进运行时」有本质区别：运行时推断错误是静默的，输入层推断错误在 30 秒的连接测试里必然暴露。
- 凭证安全不做任何「简化」：加密存储、不回显、https 传输约束、日志过滤四条全部是硬约束，不随主路径简化而妥协。
