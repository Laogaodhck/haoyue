## 1. 执行摘要

### 1.1 总体判断

haoyue 已完成从「能用」到「工程健全」的跨越：读写双路径 jail（`PathGuard.cs` / `ToolTypes.cs:79-114`）、一次性审批登记簿（`ApprovalRegistry.cs`）、124 方法契约单源治理（`contracts/daemon-contract.json`）、CI 四作业全绿、端到端审查 21 项问题 20 项闭环。**当前瓶颈不在功能缺失，而在四个结构性层面：**

1. **本地推理体验的「默认值失当」**——模型预热默认关闭（`HaoyueConfig.cs:333` 无初值即 false）、GPU 后端缺失仅 stderr 警告一次（`LocalLlmClient.cs:51-61`，桌面用户不可见）、并发与 KV 前缀复用互斥（`LocalModelCache.cs:118,124`）。这三项叠加，使「有 GPU 的用户仍在 CPU 后端上承受数量级级慢速」成为本地体验的最大单点浪费（同机实测 CUDA 25s vs CPU 3m45s）。
2. **观测与运维的「点资产丰富、线不通」**——遥测埋点质量很高（`InferencePerformance.cs`）但无消费方；事件基类无 turnId（`RuntimeEvents.cs:7`）；daemon.log 只是桌面旁路产物，CLI/独立 daemon 场景零落盘；约 199 处 catch 静默吞错。
3. **从单用户向小团队/隐私敏感演进的「安全纵深不足」**——Computer Use 一启用即获得 profile 级无沙箱 shell（`ComputerExecTool.cs:58-60`）；用户同意机制只覆盖 bash 守卫单点；知识库 URL 导入绕过网站白名单（SSRF 放大面）。
4. **规模化的前夜缺口**——知识库检索是全内存 O(N) 扫描（自定位「tens to hundreds of entries」，导入侧却 200 chunk/文件）；插件体系无签名真实性、无版本治理、marketplace README 宣传的 CLI 命令不存在（文档漂移实锤）。

**战略判断：下一阶段主题是「默认值正确化 + 可观测地基 + 安全纵深 + 数据质量管线」，而非新功能扩张。** 全部 7 维度 41 项改进均可本地闭环，满足离线与隐私约束。

### 1.5 前提与假设

- **部署语境**：单用户/小团队本地部署；消费级 GPU（8-16GB VRAM）为主；数据隐私敏感（知识/对话不出本机）；可能离线运行；Windows 为主战场（保留 Linux/macOS 适配）。
- **架构红线不可破**（详见 6.2）：PromptSlot 缓存稳定性契约、隔离运行时不复用、daemon 单写者泵、30s first-event 受理帧、hybrid 模型禁 KV 复用、GPU 构建必须 `-p:LlamaBackend=Cuda12`。
- **容量假设**：工作量按「1 名全职开发 + AI 辅助」粗估人周；若容量受限，裁剪线见 3.5。
- **度量基线**：GPU prefill 26.6k tok ≈ 7.4s；one-shot ≈ 13s；MCP 全量连接 ≈ 3.7s；隔离运行时每回合 1.5ms（p95 6.3ms）。

## 2. 分维度详述

### 2.1 维度 1：对话框交互体验增强

#### 2.1.1 现状诊断

1. **流式渲染是「全量重解析」架构，长回复性能瓶颈只治了标。** delta 按 50/120/250ms 三档窗口合并（`daemon-event-handler.ts:72-81`）、滚动节流 120ms、流式期跳过 hljs/katex 已落地（H16）；但根因未除——`MarkdownMessage.vue:106-117` 的 rendered computed 仍对整篇累计内容跑 markdown-it 全量解析，flush 窗口随长度放大（>30k 字 250ms），总解析量随回复长度呈平方级增长；fence 保护/还原再添一个 N 次全串 replace 因子（`MarkdownMessage.vue:81-89,112-114`）。无单条气泡分段渲染；会话级虚拟滚动存在（>60 条，`App.vue:1347-1382`）但 messageHeights 缓存从不清理（`App.vue:165`）。
2. **消息操作「功能全但版本模型是单线破坏性」。** regenerate 先 truncate 再重发（`App.vue:1406-1443`），旧答案不可恢复不可对比——本地模型一次「不如上一版」的重生 = 13s 起且原文已毁；无单条消息删除（删除只到线程级，`thread-actions.ts:168-187`）；分叉是真后端分叉（`App.vue:974-1050`）但无分支对比视图。
3. **工具调用可视化「能看不能交互」。** 入参/结果是裸文本（`ConversationMessage.vue:319-323`、`ToolsPanel.vue:218-225`），JSON 无高亮无复制；失败行无「重试/复制错误/查看建议」任一动作；执行中工具行无「已等待 Ns」，长往返工具看起来像卡死。
4. **输入区缺口**：无 slash 命令、无语音；Enter 发送不可配置；文件附件是「路径引用」而非内联（`app-helpers.ts:105-119` 把文件名拼进 prompt 让模型自己读，PDF/大文件被漏读时用户无感知）；提示词优化 420s 超时且无取消手段（`App.vue:1957-1966`）。
5. **会话管理缺口**：无置顶；**会话无法导出**（saveTextFile 通道仅用于知识库导出与诊断包）；**滚动位置不恢复**（`App.vue:1257` 无条件强制回底，长会话读到一半切走再回阅读位丢失）。
6. **一个「读数说谎」缺陷 + 工程面巨类。** composerCaption 用**跨轮累计** totalInputTokens（`daemon-event-handler.ts:382` 每轮 `+=`）除以模型窗口（`App.vue:339-341`），10 轮会话每次 20k 即显示 200k/128k ≈ 156%，轮数越多高估越多（项目总监已复核属实）；modelRef 采集了但从不渲染，用户看不到哪条回答出自哪个模型；19 个 >300 行文件（App.vue 2392 行），ADR-20261015 裁定「不拆只冻」；39 个 .vue 零组件测试（241 用例全在纯 .ts 逻辑）。

### 2.2 维度 2：推理速度与资源占用优化（含模型加载优化）

#### 2.2.1 现状诊断

1. **冷启动加载等待是本地首字延迟主项，且预热默认关闭。** `AgentConfig.LocalModelPreload` 无初值即 false（`HaoyueConfig.cs:333`）；实测 gemma-4-E4B（5.3GB）冷加载 7.0s，预热后首请求 4.3s（-39%）。`LocalLlmClient.FirstOutputTimeout` 15 分钟兜底的注释自认：CPU 后端 25k token 系统提示 prefill 实测上限约 14 分钟。PreloadAsync 机制与 `model.load.progress` 广播已落地（`DaemonServer.cs:2245-2259`）——缺的是默认开启与桌面就绪前可见。
2. **GPU 后端缺失只有 stderr 一次性警告，桌面用户无感知。** `WarnGpuBackendMissingOnce`（`LocalLlmClient.cs:51-61`）进程内一次；daemon+桌面场景用户看不到。同机 CUDA 25s vs CPU 3m45s（11 倍）——「GPU 可用但未被利用」是本地速度体验最大单点浪费。
3. **并发默认串行，且并发>1 即永久失去 KV 前缀复用。** `MaxConcurrency` 默认 1（`LocalModelCache.cs:118`），`SupportsPrefixReuse => MaxConcurrency <= 1`（:124）。BackgroundTaskService（MaxConcurrent=4）与 ScheduleService 在本地模型场景下全部排在同一个 `_inferenceGate` 上——「多 Agent 并行」在本地模型下无加速且各自付全量 prefill。
4. **TTFT 遥测口径把权重加载等待算进 prefill 速率，指标被系统性污染。** `InferencePerformance.cs:6-11` 注释自承认；冷启动 7s 加载被摊进 prefill tok/s，误导 ubatch 调优判断（CUDA 方案 §3.3 第二层正需要干净口径）。
5. **AdaptiveInferenceTuner 三个盲区**：KV 估算固定按 32k 上下文（`AdaptiveInferenceTuner.cs:129`）而实际 contextSize 由 `BuildContextParams` 独立决定；`OnObservation` 只消费 decode tok/s，prefill/TTFT 不参与调档（:198-231）；`LastCacheHitRate` 未作档位决策输入。
6. **多模态本地路径强制全 CPU 且不参与 KV 复用**（已知取舍，如实标注）：带图请求一律 forceCpu（`LocalLlmClient.cs:317-325`，gemma4 混合架构 CUDA 病态慢：266 图像 token 在 3070 Ti 上 26 分钟 vs CPU 23 秒）——本地视觉回合每轮全量 prefill。
7. **本地模型 tool calling 整体关闭**：`ProbeToolCallingAsync` 对 local 直接返回 Unsupported（`ProviderManager.cs:531,536`），Agent 探测失败后剥离全部工具（`Agent.cs:382-389`）——本地用户无法使用 delegate_task/delegate_tasks，是「本地优先」定位与「多 Agent 协作」之间的最大结构性缺口（属能力诚实设计，但应在产品层明示）。
- **现状更正（项目总监复核补录）**：空闲权重回收**已落地**——`LocalModelIdleUnloadMinutes` 默认 20 分钟（`HaoyueConfig.cs:327`），daemon 每 5 分钟一轮归还（`DaemonServer.cs:89,2086`）。改进点是「可见与可配」，不是从零建设。

#### 2.2.2 改进方案

| # | 措施 | 思路与落点 | 预期收益 | 可行性 | 适用场景 | 工作量 |

### 2.3 维度 3：多 Agent 调度与协作机制

#### 2.3.1 现状诊断

1. **无 DAG/无共享黑板是已裁决架构决策，不是遗漏——但并行子任务互相不可见是真实能力缺口。** `TurnExecutionScope.cs:29-33` 明言「Deliberately NOT a prospective workflow graph」；2026-10-07 编排裁决五项理由定论。现状下 `delegate_tasks` 的 2-6 个子代理零协作：无中间结果共享、无依赖表达（「B 依赖 A 的输出」只能父代理串行化两次 delegate_task）；聚合靠文本拼接（`DelegateTasksTool.cs:63-79`）。
2. **子代理上下文完全隔离，token 开销全额重付。** 子代理 = 新 Agent 实例 + 新 session（`AgentDelegation.cs:213-218`），工具 schema 明示「描述必须包含它需要的全部信息」（`DelegateTool.cs:23`）；子代理首步全量合成系统提示（工具 manifest 数千 token）。本地模型下每个子代理还各自付一次全量 prefill（26.6k tok ≈ 7.4s），且全部排在串行 inference gate 上（维度 2 诊断 3）——这是「多 Agent 协作」当前最大的隐性成本。
3. **并发与配额：深度/批量已有硬钳，缺每回合委派总数与子代理 token 预算。** 已有 `DelegationMaxDepth` 1..4（并行子代禁再委派）、单批 ≤6 超量显式报错（M4 已落地）；缺口：无每回合委派总数配额（四组件加强方案 L-E 未做项）；父回合预算闸门只累计主循环 usage（`Agent.cs:331-355`），`AgentTurnResult` 不带 usage——子代理烧的 token 不进父回合预算，最坏 6 个子代理各跑满 MaxSteps=40。
4. **取消/超时：回合级 CT 级联与 steering abort 已到位；缺子代理独立超时。** ct 从 `RunTurnAsync` 透传到子代理（`AgentDelegation.cs:218`）；steering abort 可停在途工具批次（M-B 已落地）；ScheduleService 有 1800s 墙钟。缺口：单个 delegate_task 无独立超时——一个卡死子任务拖死父回合直到总墙钟。
5. **人工审批已有但覆盖面窄。** `ApprovalRegistry` + builtin-bash-guard 拦截时一次性审批，120s 超时按拒绝（`Agent.Tools.cs:110-130`）；仅覆盖 bash 高危守卫启发式拦截；用户自定义 deny 规则硬拒绝不走审批；文件写入、MCP mutating 工具无审批钩子。
6. **长任务持久化：崩溃对账已有，断点续跑没有。** `ActiveTurnJournal` 回合开始/结束原子重写 + 变异步骤追加快照，崩溃后 `agent.interrupted` 返回中断清单；`agent.undo` LIFO 撤销。缺口：恢复=「告知用户中断了什么」，不是「从中断步骤继续」。

### 2.4 维度 4：本地知识库管理

2. **用户同意（consent）机制覆盖面极窄。** 唯一交互式审批 ApprovalRegistry 只挂在内置高危 bash 守卫一种拒绝上（`Agent.Tools.cs:110-130`），120s 超时按拒绝；花钱类（image_generate）、外发数据类（web_fetch、MCP 工具）、系统控制类工具没有任何分级提示，只有 system/permissions 提示词软约束和 read-only mode 粗粒度门。
3. **路径 jail 实际上很扎实，但只覆盖 FILE 工具两兄弟。** 读路径拒绝凭据目录（.ssh/.gnupg/.aws/.docker、*.pem/.key、cookies.sqlite 等，`PathGuard.cs:16-25`）；写路径锁死 workspace root + 拒 .git/.env/audit（`ToolTypes.cs:79-114`）。但报错文案自己承认出口——「or run it through the bash tool where the audit trail applies」（`PathGuard.cs:84`）：bash/computer_exec 可到任何路径；MCP 工具完全在 jail 之外（进程级任意能力）。
4. **静态加密只到「凭据级」，不到「数据级」。** haoyue.db（会话全文、知识库全文、向量 BLOB）是明文 SQLite（`HaoyueDatabase.cs:166-348`）；config.json 中 provider key 已 DPAPI 化（`ConfigStore.cs:335-364`），MCP OAuth/连接器 secret 同 secret: 前缀；但非 secret 类配置与 workspace config.json 明文，audit JSONL 明文 + 仅 6 类凭据正则脱敏。隐私口径校准：「数据不出本机」成立（usage.jsonl 只记 token 不记内容），但「本机其他进程读不到」不成立。
5. **审计覆盖面不全且不可防篡改。** 覆盖 mcp__*、write_file、edit_file、computer_exec 及 Mutating 工具（`ToolAudit.cs:46-59`）——不含 knowledge_save/forget、fact_save/forget、approval 三态、connector install/uninstall、skill import、mode 切换；无哈希链/HMAC，同权限可改写。
6. **网络外发控制不统一。** web_fetch 与 browser open 都过 WebSiteAllowlist（`WebTools.cs:316-317`、`BrowserTool.cs:92-98`），但**知识库 URL 导入不过白名单**（`KnowledgeWeb.cs`，15s 超时+3MB 上限），内网地址无过滤——模型可把内网页/元数据灌进知识库再进 prompt，构成 SSRF 放大面；embedding 请求会把知识正文发往配置的 provider，semantic.status 只显示模型名不显示目的地；bash 内 curl/wget 天然绕过白名单。正面：MCP OAuth 用 PKCE+loopback+state，TLS 无自定义校验降级，daemon token 文件 ACL 收紧 + 常数时间比较（`DaemonAuth.cs:36-86`）。

### 6.2 架构红线（改进方案不得违反）

1. PromptSlot 顺序即 prompt 前缀缓存稳定性契约：Skill 段必须置于 Tool/Memory 段之后；工具 schema 按 Ordinal 排序；thinking 历史不回传。
2. 隔离运行时每回合 1.5ms 已压测定论：不按 workspace 复用（隔离性是并发正确性红线）。
3. Daemon 连接写纪律：所有对连接 writer 的写帧必须在 daemon 消息循环路径完成；后台任务只发 runtime 事件。
4. 桌面 chat 30s first-event 超时；daemon turn 启动即回 status("Preparing turn") 受理帧。
5. nemotron_h 等 Mamba2 hybrid 架构模型禁用 KV 前缀复用。
6. NVIDIA 机器构建必须 `-p:LlamaBackend=Cuda12`（csproj 默认 CPU 后端，GpuLayers 会静默失效）。
