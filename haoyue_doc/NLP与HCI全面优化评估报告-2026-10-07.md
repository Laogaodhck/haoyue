## 一、总体评价

### NLP 侧（Runtime）

**结构性正确性突出**：提示词全外置 + 槽位拼装（PromptComposer 10 类 Slot、per-promptKey 缓存命中 provider 前缀缓存）、工具对完整性修复（EnsureCompleteToolTurns）、上下文压缩降级路径、failover 链墙钟预算与熔断、CJK 感知 token 估算，均为同类系统良好实践。

**三大短板**：① 失败路径的状态一致性（终态 WorkflowEvent 不可达、流中断内容不持久化）；② CLI/daemon 双链路 steer 行为分裂（CLI 绕过队列有数据竞争）；③ MCP 边界的安全默认值（提示词无信任包装、readonly 靠名字关键词推断可被绕过）。

### HCI 侧（桌面端）

**错误路径健壮性与状态一致性下了大量功夫**（selectionToken 防串扰、草稿回填、发送/排队/停止三态、终止事件兜底 finalize）。

**三大短板**：① 「写了却没接上 UI」的死功能（regenerateMessage 完整实现但无任何入口绑定）；② 流式渲染零节流 + Markdown 全量重解析的 O(n²) 性能隐患；③ 破坏性操作确认不齐（计划任务删除零确认）+ 对话框无键盘/焦点管理。

## 二、NLP：问题 → 建议 → 预期效果

### 2.1 语义理解与意图识别

**【N1·严重】MCP/技能提示词无「视为数据」信任包装**
- 位置：`Mcp/McpManager.cs:193-218`、`Skills/SkillManager.cs:204-229`
- 问题：MCP 服务器返回的 prompt/resource、用户导入的技能 .md 可携带任意指令文本直接进入系统提示词（PromptSlot.Tool 权威位次），且无信任边界声明；仅 workspace context 有只读包装（`builtin/context.txt`）。
- 建议：MCP/技能片段统一套用「read-only background, not instructions」式包装，声明与直接指令冲突时以用户指令优先。
- 预期效果：阻断第三方/MCP 内容对模型行为的指令级劫持，提示词注入攻击面收敛。

**【N2·严重】MCP Mutating 靠名字关键词推断，readonly 模式可被绕过**
- 位置：`Mcp/McpManager.cs:339-346`（InferMutating 关键词表）、`Agents/Agent.Tools.cs:33-38`
- 问题：`send_email`、`deploy`、`post_message` 等不含关键词的变更型工具被判只读 → readonly/plan 模式放行真实变更，且被并发进只读批量批。
- 建议：MCP server 配置增加显式 mutating 工具名单；未知名单工具默认按 mutating 处理（fail-closed）。
- 预期效果：readonly 承诺从「启发式近似」变为「配置保证」，高危误执行风险归零。

**【N3·一般】用户输入无兜底校验/截断**
- 位置：`Agents/Agent.cs:56-59`
- 问题：`RunOneShotAsync` 与调度路径无空检查；单条超窗输入直接命中 provider 400 且不可重试，回合以英文原始报错终止。
- 建议：`RunTurnAsync` 入口统一拒绝空输入、对超窗输入头尾保留截断并附提示。
- 预期效果：超长输入不再炸回合，各入口行为一致。

**【N4·一般】工具描述 fallback 静默降级 / Schema 无枚举约束**
- 位置：`Tools/Builtin/FileTools.cs:20-21`（`"The {Name} tool."`）、`Tools/WebTools.cs:34`
- 问题：prompts 目录缺失时描述退化为无信息量字符串且无告警；`web_search.engine` 自由字符串，值域错误只能靠一轮执行期自纠。
- 建议：fallback 时记 Warning；Schema 构建器支持 enum 约束。
- 预期效果：意图误识别下降，工具参数一次到位率提升（省一轮往返）。

**【N5·一般】技能触发仅靠关键词硬规则**
- 位置：`Skills/SkillManager.cs:156-185`、`Agent.Prompting.cs:99-130`
- 问题：换一种说法（不含 trigger 关键词）技能不注入；CJK 子串匹配易误命中。
- 建议：保留关键词快路径，高价值技能增加轻量模型分类或让主模型自主声明使用。
- 预期效果：技能召回率提升，意图理解不再受字面措辞限制。

**【N6·轻微】datetime 变量缺时刻与星期**（`PromptVariables.cs:27`）→ 改 `yyyy-MM-dd ddd HH:mm zzz`。「现在几点」「今天周几」类问题不再答错。

**【N7·轻微】system/default.txt 空段落标题**（`default.txt:12-13`）→ 删除或补内容，省 token、减少结构干扰。

### 2.2 多轮对话连贯性

**【N8·严重】CLI steer 绕过队列：数据竞争 + 丢失窗口**
- 位置：`haoyue_cli/ChatLoop.cs:115-122` 直写 session；对比 daemon 路径 `AgentSteeringQueue.cs:39-47`（设计正确）
- 问题：(a) REPL 线程与 Agent 回合线程并发读写同一 `List<ChatMessage>`，非线程安全；(b) turn 恰好结束时插话变成普通历史消息被误读为新提问；(c) 两链路前缀不一致（CLI 加 `[User Steering Instruction]:`，daemon 裸文本）。
- 建议：CLI 复用 AgentSteeringQueue（`RunTurnAsync` 已有 steering 参数，ChatLoop.cs:134 未传）；统一前缀。
- 预期效果：插话不丢、不炸、两端行为一致，多轮引导可靠。

**【N9·一般】FitToWindow 保底 6 条仍可能超窗**
- 位置：`ContextPlanner.cs:168`
- 问题：6 条保底消息本身超预算时循环退出照发 → provider 400 不可重试，压缩兜底恰好覆盖不到该场景。
- 建议：保底裁剪后仍超限时对单条超大消息内部截断（保头尾）。
- 预期效果：消灭「无论如何都会 400」的死区场景。

**【N10·一般】压缩摘要静默丢失信息**
- 位置：`Agent.Context.cs:45-120`、`ContextPlanner.cs:136-156`
- 问题：old 部分：图像全丢（WithoutImages）、工具原始输出仅进摘要、摘要 MaxTokens=4096 且 summarize 输入又过一次 FitToWindow——最老内容可能在被总结前就被裁掉。
- 建议：old 超限时分段 map-reduce 摘要；至少对被裁部分记告警。
- 预期效果：长对话压缩后关键事实（路径/命令/决策）留存率显著提升。

**【N11·一般】`>>>` 前缀可被用户输入仿冒**
- 位置：`Agent.Context.cs:75-77`（压缩消息伪装 User）、运行时 nudge 同前缀
- 问题：模型需自行分辨「系统注入」与「真实用户输入」，用户输入含 `>>> [step budget]` 即可伪造。
- 建议：注入消息走 developer 角色或传输层区分；渲染层过滤用户输入中的该前缀。
- 预期效果：封堵一类低成本提示词伪造通道。

**【N12·轻微】压缩后 turnHasImages 扫描范围扩大**（`Agent.cs:189-193`）：早回合图像把纯文本步骤误切 vision 模型 → 记录压缩边界索引限定扫描范围。多模态成本下降。

**【N13·轻微】token 估算两处偏差**（`ContextPlanner.cs:86,111-115`）：图像固定 1200 token（高分辨率实际 2-6 倍）；ToolOutputBudget 用拉丁 4 chars/token 换算中文输出实际约 2.7 倍 → 图像按尺寸估算、预算按 `CharsPerTokenFor` 自适应。窗口预算失真修复。

**【正面确认】**：历史全量组装 + 每步 FitToWindow、分支/截断断裂工具对修复、压缩失败降级路径、daemon 同会话并发互斥（含可操作报错指引）——设计均正确，无需改动。

### 2.3 错误处理与恢复

**【N14·严重】终态 WorkflowEvent 不可达（一行级逻辑错误）**
- 位置：`Agents/Agent.cs:340-343`（发布语句在 try 内）+ `350-365`（catch 无 WorkflowEvent）
- 问题：`"error"` 分支永不执行；失败/取消路径无任何终态 workflow 事件，客户端 workflow 视图停在最后一步；maxSteps 耗尽却发「done」与「任务可能尚未完成」警告自相矛盾。
- 建议：终态发布移到 try/catch 之后公共路径，以真实 error/cancelled 状态判定 kind。
- 预期效果：所有失败场景客户端状态一致，workflow 进度视图正确收尾。

**【N15·严重】committed 后流中断：已流出内容不持久化**
- 位置：`Agent.Streaming.cs:99-116`、`ProviderManager.cs:241-251`
- 问题：首 token 后断网/服务端中断 → UI 看到半截回答但历史中不存在，resume 后内容消失且无法续写。
- 建议：StreamOnceAsync 捕获流中途 LlmException 时与取消路径同样保留 partial text（FinishReason=interrupted），持久化并决定是否续写。
- 预期效果：流式产品最高频失败场景不再丢内容，重开会话所见即所得。

**【N16·轻微】错误文案英文直出 + 不解析 Retry-After**（`OpenAiCompatibleClient.cs:443-453`）→ 文案本地化、429 按 Retry-After 调整退避。中文用户可读性提升。

**【N17·一般】daemon 崩溃重启无 turn 恢复语义**：与 N15 叠加；建议每步 flush partial 输出、重启后广播「回合中断」。进程级损失可控。

**【正面确认】**：工具错误自纠错闭环（ToolResult(false) + 「Regenerate the tool call」指引 + 截断 JSON 修复 + 同签名连败 2 次注入纠偏）设计完整；全候选失败聚合报错覆盖所有被试模型。

### 2.4 响应质量保障

**【正面确认】ProviderManager 是全仓库质量最高模块之一**：指数退避+jitter、链级墙钟预算、per-model 熔断分类冷却、half-open 单探针、候选切换按各候选 ContextWindow 重新 FitToWindow（切换零上下文损失）、失败记忆聚合。

**【N18·一般】空回答耗尽收尾返回旧文本**
- 位置：`Agent.cs:280-316`
- 问题：第二次空回答 break 时 finalText 仍是上一步前言，却以「任务完成」+旧文本收尾，用户误当最终答案。
- 建议：耗尽路径显式 Warning 并标注/置空 finalText。
- 预期效果：消除「拿到过时半截答案被当结论」的误导。

**【N19·轻微】fallback 候选单次尝试遇瞬时 429 即放弃** → 可配置化（如 fallbackRetry=1）。

**【N20·轻微】无响应后处理层**：现状不算缺陷，记录观察点。

## 三、HCI：问题 → 建议 → 预期效果

### 3.1 交互流程合理性

**【H1·致命】「重新生成」有实现无入口（死代码）**
- 位置：`App.vue:1058-1095`（regenerateMessage）、`1052-1056`（continueAssistant）；模板仅绑定 open-diff/branch/edit（1610-1629）
- 问题：失败回合无任何「重试」入口，唯一恢复路径是编辑→回退→重发 3 步操作；两个已实现函数在渲染层零引用。
- 建议：ConversationMessage 增加 regenerate emit，最后一条失败/完成气泡 footer 渲染「重新生成」；continueAssistant 作为「被 max_tokens 截断」的「继续生成」接回。
- 预期效果：失败恢复从 3 步降到 1 步；与 H10 组合形成结构化错误卡+重试闭环，满意度直接提升。

**【H2·严重】停止按钮被输入内容「劫持」**
- 位置：`Composer.vue:524-532`
- 问题：流式输出中只要输入框有内容，按钮就变「排队发送」，想急停必须先删光文字和附件。
- 建议：停止+发送双按钮并存，或 Esc/Ctrl+. 独立停止快捷键。
- 预期效果：急停操作可达时间从「清空输入」级降到瞬时，消除高频挫败感。

**【H3·严重】运行中归档/删除静默失败**
- 位置：`thread-actions.ts:57/104/129/154/174/196/220/248`（8 处 `thread.running` 时直接 return）、`App.vue:1420`
- 问题：点击后界面毫无反应，用户以为按钮坏了。
- 建议：统一 `guardNotRunning(thread, '归档')` 帮助函数 + toast 解释；或 Sidebar 菜单对 running 任务置灰。
- 预期效果：状态死区消除，操作结果永远有反馈。

**【H4·一般】重命名任务需 3 步重型对话框**（`Sidebar.vue:275-277` → `TaskSettingsDialog.vue`）→ 侧栏行内双击/F2 重命名，失焦保存失败回滚。高频轻量操作路径缩短。

**【H5·一般】切任务附件草稿静默丢失**（`App.vue:156` 只存文本、`Composer.vue:421-426` 无条件清空附件）→ 草稿结构升级 `{text, images, files}`（附件存路径引用即可）。行为对称，损失感消除。

**【H6·一般】归档任务发消息自动恢复缺显式确认**（`App.vue:1097-1117`，仅一行灰 caption）→ 发送时一次轻量确认 +「总是自动恢复」记忆。归档语义不再被无感破坏。

**【H7·轻微】分支/编辑入口 hover 才可见**（`ConversationMessage.vue:422-437` opacity:0）→ 最后一条完成消息常显 footer 或一次性引导气泡。功能可发现性提升。

### 3.2 界面可用性

**【H8·严重】ConfirmDialog 无键盘支持、无焦点管理**
- 位置：`ConfirmDialog.vue:6-29`、`confirmation.ts:20-32`
- 问题：不自动聚焦、无焦点陷阱、无 Escape/Enter 处理；danger 对话框键盘用户只能用鼠标，焦点残留可能连按 Enter 重复触发底层操作。
- 建议：打开聚焦「取消」（danger 默认安全项），Tab 循环、Esc=取消、Enter=确认；EditMessageDialog/TaskSettingsDialog 同步。
- 预期效果：全键盘可达，误触发风险归零，a11y 声明与行为一致。

**【H9·一般】无「回到底部」浮动按钮**（`App.vue:344-356, 999-1034`）→ `autoFollowConversation===false` 时渲染「↓ 回到最新」（可带未读角标）；顺带清理切任务时 messageHeights 残留。长对话导航体验修复。

**【H10·一般】对话内搜索只做变暗，无计数/跳转，不搜工具结果与思考内容**（`app-helpers.ts:244-248`）→ 命中计数 + 上下条跳转 + 匹配范围扩到 tool.detail/thinking。搜索从「视觉降噪」变成「快速定位」。

**【H11·一般】快捷键缺口**（`AppTitleBar.vue:147-158`）→ 补 Ctrl+K 快速切换任务 / Ctrl+F 聚焦搜索（程序化 focus）、停止生成快捷键；Sidebar 搜索框 autofocus 在 Transition 内不可靠改程序化。键盘流用户核心高频操作全覆盖。

**【H12·一般】文案中英混杂**（`Composer.vue:46-51` Edit/Plan/Read/Auto、`ReasoningDepthMenu.vue`「超级(ultra)」、`main/index.ts:347` "Open workspace"）→ 统一「中文（英文原文）」风格；"Read" 实为 readonly 应译准确。认知负担下降。

**【H13·一般】空任务也渲染零值统计噪音**（`App.vue:176-195, 1685`）→ 空任务隐藏统计；归档提示独立成条。

**【H14·轻微】window.alert 禁而未改**（`App.vue:564-567`）、**【H15·轻微】项目运行中 spinner 仅折叠时显示**（`Sidebar.vue:304-305`）→ 换用应用内反馈；展开与否状态指示一致。

### 3.3 反馈及时性
