## 一、N5：技能触发语义路由

### 1.1 现状与问题

- 注入门控：`Skills/SkillManager.cs:156-179` —— `Triggered()` 纯关键词匹配（ASCII 词边界 / CJK 子串），配合 3 轮粘性窗（`Agent.Prompting.cs:99-130`）。
- 问题：措辞不含 trigger 关键词时技能不注入（召回缺口）；CJK 子串匹配易误命中（精度缺口）。
- 联动约束：`SelectInjectedSkills` 是注入与 `allowed-tools` 工具权威的**单一事实来源**（`SkillManager.cs:142-153`、`ResolveToolPolicy`），任何新信号源都必须在这一个入口合并，否则注入与工具边界会漂移。

### 1.2 方案选型

| 方案 | 召回 | 成本 | 延迟 | 复杂度 |
|---|---|---|---|---|
| A 轻量分类模型 | 高 | 每 turn 一次 ~300-500 token 调用 | +300-800ms（可与提示词组装并行） | 中 |
| B 主模型自主声明 | 高 | 无额外调用；占系统提示词 token（技能目录） | 零额外延迟；但需一轮工具调用才注入 | 中 |
| C 混合（关键词 + 目录声明 + 可选分类器） | 最高 | 按需 | 关键词命中零开销 | 高 |

**选 C，分两阶段**：阶段 1 只做 B（无外部依赖、立即可交付）；阶段 2 加 A 作为可选增强。

### 1.3 阶段 1：技能目录 + `declare_skill` 工具（B）✅ 已实施（`bad0848`）

**目标**：关键词未命中时，主模型可根据目录中的「适用场景」声明自主加载技能。

改动点：

1. `SkillManifest` 新增 `AlwaysListed`（YAML 键 `always-listed`，默认 `true`）：是否进入模型可见目录。敏感/内部技能可设 `false` 隐藏。
2. `SkillManager` 新增：
   ```csharp
   /// <summary>模型可见的技能目录（name + 适用场景 + 已声明参数），size-capped。</summary>
   internal string RenderSkillCatalog(WorkspaceInfo workspace);
   /// <summary>按名称取技能（供 declare_skill 工具），仅限 Enabled 且 AlwaysListed。</summary>
   internal SkillInfo? FindByName(WorkspaceInfo workspace, string name);
   ```
3. 新工具 `DeclareSkillTool`（`Tools/Builtin/`，`Mutating=false`，无网络依赖）：
   - 参数：`name`（string，必填）。
   - 行为：调用 `SkillManager.DeclareForCurrentTurn(name)` → 把该技能加入**本 turn 的模型声明集合**；返回「已注入，下一轮对话生效」。
   - 注入生效时机：下一个模型 step 组装提示词时，`SelectInjectedSkills` 的结果 = 关键词命中 ∪ 模型声明集合。`ActiveTools` 同步重算，工具权威天然同源。
4. `Agent.cs` 主循环：
   - `ComposeSystemPromptAsync` 增加 `skill_catalog` 槽位（技能数为 0 时为空串，不占 token）。
   - turn 开始时清空 `_modelDeclaredSkills`（HashSet，per-turn）。
   - 关键词已命中的技能仍在目录中列出但标注「已注入」，引导模型不要重复声明。
5. 提示词（`prompts/system/default.txt` 或 skill 槽位模板）加一句：**「若用户任务匹配目录中某技能的场景但未自动注入，可调用 declare_skill 显式加载。」**

**风险与防护**：
- 模型乱声明 → `AlwaysListed` 白名单控制；目录中写明「仅在明确匹配时声明」。
- 声明后同 turn 工具权威扩张 → 只影响后续 step，与现有 allow-list 语义一致，可接受；文档注明。

**测试**：
- `RenderSkillCatalog` 包含 Enabled+AlwaysListed 技能、排除 disabled 与 `always-listed: false`。
- `DeclareSkillTool` 声明后下一 step 注入 + allowed-tools 联动。
- turn 边界：声明集合不跨 turn 泄漏。

### 1.4 阶段 2：可选分类模型（A）⏸ 暂缓（观察阶段 1 召回数据后再定）

**配置**（`HaoyueConfig.cs` → `AgentConfig`）：
```csharp
public SkillRoutingConfig SkillRouting { get; set; } = new();
public sealed class SkillRoutingConfig
{
    /// <summary>keyword（现状）| hybrid（关键词 + 分类器）。</summary>
    public string Mode { get; set; } = "keyword";
    /// <summary>分类用模型引用，如 "provider/model-id"；null 时 hybrid 降级为 keyword。</summary>
    public string? ClassifierModel { get; set; }
    /// <summary>分类调用超时，超时静默降级为仅关键词。</summary>
    public int ClassifierTimeoutMs { get; set; } = 1500;
}
```

**流程**（`Agent.RunTurnAsync` 组装提示词前）：
1. 取 Enabled 且带 Triggers 的技能清单（≤20 条），组装分类请求：用户消息 + 每条技能的 name/description/triggers，要求返回 JSON 数组（命中的技能 name）。
2. `Task.WhenAny(分类任务, Task.Delay(timeout))` —— 超时/异常/解析失败一律**静默降级为仅关键词**，绝不阻塞或失败主 turn。
3. 结果并入 `SelectInjectedSkills` 的第三个信号源：`Triggered(manifest, context, classifierHits, modelDeclared)`。
4. 粘性窗语义保持：后续 turn 的分类请求附带同窗历史，避免「继续」丢技能。

**成本估算**（20 技能清单 + 400 字输入）：约 600-900 input token / turn，输出 <50 token。用廉价小模型（如各 provider 的 mini/flash 档）成本可忽略；默认 `Mode=keyword` 不改变任何现有行为。

**测试**：分类命中注入、超时降级、坏 JSON 降级、hybrid 下工具权威与注入同源断言。

### 1.5 交付切分

- 阶段 1：一次提交（SkillManager + 新工具 + 提示词 + 测试），预计 6-8 文件。
- 阶段 2：独立提交（Config + 分类调用 + 测试），默认关闭。

## 二、N17：daemon 崩溃后的 turn 恢复语义

### 2.1 现状与缺口

1. **partial 丢失**：`Agent.Streaming.cs` 的 partial 保留只覆盖 `LlmException`/取消路径（N15 已修）；进程被杀不走 catch，`streamedText` 随进程消失。
2. **无持久 running 标记**：`thread.running` 是客户端本地状态；daemon 重启后 `session-sync.ts:124`（`if (thread.running || thread.assistantId) return`）会跳过正在 running 的 thread 的重载 → **spinner 永久卡死**。
3. **无中断告知**：客户端只能靠连接断开来猜测，重连后无任何「上次回合中断」提示。

### 2.2 设计原则

- **不自动续跑**：工具可能执行到一半（文件改了一半、命令发了一半），自动重跑有副作用风险。恢复语义 = **保留现场 + 明确告知 + 一键重试**（复用 H18 错误卡的 regenerate 通道）。
- **进程级损失可控**（报告已定性）：目标是把「丢失」收敛到当前 step 的流式尾巴，而非整轮。

### 2.3 方案：三部分

#### A. 流式 partial 周期落盘（Runtime）⛔ 经评估降级不实施

> 降级理由（即本方案 2.5 第三条风险条款被触发）：占位消息会改变历史消息数量，影响 `turnMessageIndex` 与 N12 图像增量跟踪的影响面核对成本超过收益——崩溃丢失已收敛到约 2s 流式尾巴，恢复提示（B）+ 不自动续跑已覆盖用户感知。落地时直接采用降级形态：「仅中断说明消息，不保留 streaming partial」。

- `ISessionStore` 新增：
  ```csharp
  /// <summary>流式期间 upsert 最后一条 assistant 消息的文本（崩溃现场保留），非流式路径不得调用。</summary>
  void UpdateTrailingAssistant(AgentSession session, string text, string finishReason);
  ```
- `SessionStore` 实现：若最后一条消息是本 turn 的 assistant 占位（turn 开始时 `Append` 一条空文本占位消息，标记 `state=streaming`），就地更新其 Text；文件写入节流 **≥2s 一次**（复用流式 50ms 合并窗之外的独立计时器），turn 正常收尾时由现有 `finalText` Append 逻辑覆盖为最终版（避免双写冲突：收尾时改为更新该占位消息而非再 Append）。
- `Agent.Streaming.cs`：流式循环内在节流窗口到期时调用 `UpdateTrailingAssistant`；`FinishReason` 中间态写 `"streaming"`。
- **权衡**：2s 粒度下崩溃最多丢 2s 输出；会话文件为 JSON 全量写，单会话通常 <1MB，IO 可接受。

#### B. 崩溃标记与启动恢复（Runtime）✅ 已实施（`1ac92d3`，N17-B）

- 活跃 turn 注册表：`DaemonServer` 维护 `~/.haoyue/active-turns.json`（turn 开始写入 `{sessionId, startedAt}`，正常结束删除；进程死亡自然残留）。
- 启动时（`DaemonServer` 构造完成、accept 连接前）：
  1. 读取 `active-turns.json`，对每个残留 session：
     - 若最后一条 assistant 消息带 streaming partial → 追加系统提示消息「⚠ 上次回合因 Runtime 异常退出而中断，上方为中断前输出（可能不完整），可点击重新生成继续」。
     - 无 partial → 同样追加中断说明。
  2. 清空该文件。
  3. 通过 `EventJournal` 持久化一条 `TurnInterruptedEvent(sessionId, reason="daemon_crash")`，daemon 起来后向连接的客户端广播（客户端重连后能收到或通过 `session.resume` 拉到）。
- `ChatMessage` 不需要新字段：中断标识复用现有 Warning 文本约定（桌面端按前缀识别即可，与 H17 interrupted 徽章的判定并存）。

#### C. 客户端恢复（Desktop）✅ 已实施（`297af93`，N17-C）

- `daemon-event-handler.ts` 新增 `turn.interrupted` 事件处理：
  - `thread.running = false`、清 `assistantId`；
  - 气泡打 interrupted 徽章（复用 H17 的 `interrupted` 字段，文案「上次回合被 Runtime 重启中断」）；
  - toast 通知。
- `session-sync.ts:114-124`：重连恢复路径放行——`runReconnectCycle` 恢复任务时对 `thread.running === true` 的 thread 强制 `reloadThreadSession`（加 `force` 参数），消灭 spinner 卡死。
- `App.vue` reconnect toast（H24 已有「恢复了 N 个任务」）补充：若有中断 turn，文案追加「其中 M 个任务上次回合被中断」。

### 2.4 测试计划

| 层 | 用例 |
|---|---|
| SessionStore | `UpdateTrailingAssistant` upsert 语义；turn 收尾覆盖为最终版不双写 |
| Agent.Streaming | 节流窗口内多次 delta 只落盘一次；取消/异常路径 final 覆盖 |
| DaemonServer | 残留 `active-turns.json` → 启动追加中断消息 + 清文件 + 广播 TurnInterruptedEvent |
| Desktop handler | `turn.interrupted` → running=false + interrupted 徽章 + toast |
| session-sync | 重连时 running thread 强制重载（mock daemon 断言 `session.get` 被调用） |

### 2.5 风险

- `UpdateTrailingAssistant` 与正常收尾的并发写 → 同一 turn 内串行（流式 flush 与收尾都在 turn 异步流上），加锁防护即可。
- `active-turns.json` 写入失败 → try/catch 吞掉，退化为「无恢复语义」，不影响主流程。
- 占位消息方案会改变历史消息数量（turn 开始即 +1）→ 影响面：`turnMessageIndex`、图像跟踪（N12 增量逻辑）、测试断言。实施时需逐一核对；若影响面过大，降级为「仅中断说明消息，不保留 streaming partial」（B 部分不变，损失仍是整 step）。
