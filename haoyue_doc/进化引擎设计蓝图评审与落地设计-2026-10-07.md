# 进化引擎设计蓝图评审与落地设计（2026-10-07）

> 输入：用户提出的「Haoyue 进化引擎 (The Evolution Engine) 设计蓝图」——从"指令→执行→结果"线性模型升级为"失败→反思→假设→实验→结构升级"的元认知层，含四个模块：A 缺陷与差距追踪器、B 假说生成器、C 隔离沙箱、D 补丁管理器。
>
> 性质：架构提案裁决 + 可落地设计。与《工作流编排层架构裁决与TurnScope设计》同模式：先对照代码核实前提，再裁决采纳范围。

---

## 一、总体裁决

**理念采纳，形态收缩。**「反思-迭代闭环」方向成立，但蓝图按"服务端平台"假设设计（Docker、流式监控、CI/CD、LLM 自改代码），与 haoyue「Windows 单机桌面运行时 + 技能即数据」的现实错位。落地形态收敛为一句话：

> **一个挂载在现有 Scheduler 上的定时/手动"反思 turn"，从 SQLite 事件账本聚合缺陷信号，产出候选技能（数据态资产），在临时工作区用现有验证链做实验，最终经桌面端 diff 审批人工合入。**

不引入：Docker 容器、流式监控新层、LLM 自改 C# 代码、自动合并。
复用：JournaledEventBus / ScheduleService / BuildVerifier / TurnExecutionScope / SkillManager / declare_skill——六个现有设施正好拼出闭环，**无需新的编排框架**（与 Workflow Graph 裁决同理）。

## 二、逐模块核实（对照代码证据）

### A. Defect & Gap Tracker —— 一半成立

| 蓝图主张 | 现实核实 | 结论 |
|---|---|---|
| 实时监控 EventBus 捕获失败 | `JournaledEventBus` 已把 `ToolCallCompletedEvent(Success=false)`、`ErrorEvent`、`WarningEvent`、`VerificationCompletedEvent(Success=false)`、`TurnCompletedEvent(Error≠null)`、`ProviderRetryEvent` 持久化进 SQLite（`EventJournal.PersistentTypes`，保留 5000 行，`Events/EventJournal.cs:21-31`） | ✅ 信号已落盘，**不需要新监控层**——离线查询 journal 表（批处理）优于流式订阅 |
| LLM 输出信心度低 (Low Confidence) | 运行时无 confidence 信号；主流 Provider API 也不返回置信度 | ⛔ 不可实现。替换为可观测代理信号：同一工具短窗口连续失败、验证链 N 次失败后修复成功（"带病通过"）、`declare_skill` 失败 |
| 能力差距检测 | `declare_skill` 对不存在技能返回 Fail（`Skills/DeclareSkillTool.cs:31`）；工具参数校验失败走 `ToolResult.Fail` | ✅ 真实信号存在，可直接定义 Gap |
| 上下文快照 (Context Snapshot) | 会话与事件均已入 SQLite（WAL）；`TurnCompletedEvent.SessionId` + journal 可按 SessionId 拼装失败时序 | ✅ 无需新建快照机制，按 SessionId 回放即可 |
| 用户明确负反馈 | 现有 `UserSteerEvent`（用户插话纠正）是唯一弱信号；无"做错了"结构化通道 | ⚠️ 阶段一以隐式信号为主，负反馈通道列为后续（桌面端加 thumbs-down 按钮 → 写入 journal 的新事件类型，成本很低） |

**改造后的 A**：`DefectAggregator`——纯查询组件，从 `events` 表聚合出结构化 `DefectReport`（失败工具序列、SessionId、时间窗、Gap 类型、根因假设素材）。不订阅总线、不在线运行。

### B. Hypothesis Generator —— 成立，且宿主已存在

| 蓝图主张 | 现实核实 | 结论 |
|---|---|---|
| 专门"架构师 AI"分析缺陷报告、生成 2-3 个差异化假说、输出 TestPlan | haoyue 本身就是 LLM agent 运行时；`ScheduleService` 已支持 cron 驱动完整 turn（`Scheduling/ScheduleService.cs`） | ✅ 反思 turn = 一次普通 agent turn + 专属反思 prompt + 输入 DefectReport。**零新编排设施** |
| 输出 TestPlan（MRE + Success Criteria） | MRE = 临时工作区内的最小复现文件集；Success Criteria = workspace `verifyCommands` 验证链（`Verification/BuildVerifier.cs:21`） | ✅ TestPlan 不需要新对象模型——就是"一段生成的工作区 + 验证命令清单"，用现有概念表达 |
| 修改工具参数 / 核心 Prompt 指令优先级 | 工具与核心 prompt 在 C# 代码内 | ⛔ 裁决：**LLM 不自改代码**。自改范围限定为数据态资产：技能目录（`skill.yaml` + `prompt.txt`）、workspace 配置的验证命令。这正合"技能即数据"架构——技能层本来就是设计给非代码扩展用的 |

**改造后的 B**：反思 turn 的产出物只允许是——① 新技能目录草稿；② 现有技能的 `prompt.txt`/`skill.yaml`（triggers/allowed-tools）修订；③ 无行动结论（判定为环境问题/误报）。禁止触碰运行时代码与全局配置。

### C. Sandbox —— Docker 裁决不引入，换轻量沙箱

| 蓝图主张 | 现实核实 | 结论 |
|---|---|---|
| Docker/容器隔离实验代码 | haoyue 面向普通用户 Windows 桌面，Docker 不是可假设存在的依赖 | ⛔ 不引入容器。实验对象本身也只是**数据文件**（技能提示词），非可执行注入，文件级风险天然可控 |
| 输入受限（只用 MRE 数据集） | — | ✅ 用临时实验工作区实现：反思 turn 复制 MRE 到 `<workspace>/.haoyue/labs/<turn>/`，实验只在此目录内进行 |
| 安全兜底 | 刚落地的 TurnExecutionScope 提供文件级账本+补偿回滚；manifest v2 `allowed-tools` 提供工具权限边界（`Skills/SkillManager.cs:31`） | ✅ 四层轻量沙箱：**临时工作区（范围受限） + 工具白名单（能力受限） + 验证链门禁（结果受限） + TurnScope 补偿（可回滚）** |

实验 turn 的安全配置即一次普通技能调用：反思技能 manifest 声明 `allowed-tools: [read, write, edit, bash, declare_skill]`，write/edit 的补偿注册自动生效。

### D. Patch Manager —— 成立，去 CI/CD 化

| 蓝图主张 | 现实核实 | 结论 |
|---|---|---|
| 候选补丁不直接生效，走审查流程 | SkillManager 每次扫描目录即热加载（`~/.haoyue/skills` + `<workspace>/skills`），同目录落盘即生效 | ✅ 因此"候选态"只需独立目录：`~/.haoyue/skills/<name>.candidate/`——不带 `.candidate` 后缀的目录才被加载（扫描侧加一行过滤，或候选先放在 `~/.haoyue/skills-candidates/`） |
| Git 实验分支 | 用户工作流本身即 git 驱动；技能目录可纳入 git | ✅ 保留：候选补丁以 diff 形式落盘 + 桌面端审批 UI |
| 版本号 + 原因描述 + 人工确认合并 | 桌面端已有横幅/表单 UI 模式（撤销横幅、MCP 表单）可复用 | ✅ 审批卡展示：缺陷报告摘要 → 假说 → diff → 实验验证结果，人工「采纳/丢弃」。CI/CD 对单机应用过重，**本地验证链通过 + 人工确认**即发布门禁 |

## 三、落地架构（E1-E4）

```
SQLite events 表（已有，失败信号已持久化）
        │
        ▼
E1 DefectAggregator（查询组件，离线聚合 → DefectReport）
        │  手动触发（RPC evolution.inspect）或 cron 触发
        ▼
E2 反思 turn（ScheduleService 驱动 + 反思技能 prompt）
        │  输入 DefectReport；输出：候选技能 / 技能修订 / 无行动结论
        ▼
E3 实验区（.haoyue/labs/<turn>/ 临时工作区 + MRE
        + verifyCommands 验证链 + allowed-tools 白名单 + TurnScope 补偿）
        │  验证链通过 → 候选补丁落盘 skills-candidates/
        ▼
E4 审批（桌面端候选卡：缺陷→假说→diff→验证结果，人工采纳/丢弃）
        │  采纳 → 移入 skills/ 正式目录（SkillManager 热加载生效）
        ▼
   下一轮运行产生新事件 → 闭环
```

### 关键数据对象（最小定义）

- **DefectReport**：`{ id, window, signals[], sessionId?, gapType?, hypothesis-seeds }`——signals 为 journal 聚合出的失败序列（工具名、次数、错误摘要、验证链失败片段）。
- **候选技能**：目录 `skill.yaml + prompt.txt + rationale.md`（rationale 记录缺陷来源与假说，即蓝图要求的"版本号+原因描述"，用日期戳代替版本号）。
- **审批记录**：采纳/丢弃 + 时间，追加写入 `evolution-log`（复用 events 表新事件类型 `EvolutionDecisionEvent`，自然获得持久化与桌面端可见性）。

### E1 信号规则（初版三条，全部可从现有事件表推导）

1. **工具失败簇**：同一 `(toolName, normalizedError)` 在 30 分钟窗口内失败 ≥3 次。
2. **修复循环挣扎**：`VerificationCompletedEvent(Success=false)` 连续 ≥3 次后最终通过。
3. **能力差距**：`declare_skill` Fail（技能不存在）+ 工具参数校验反复失败。

不做 confidence 信号（不存在）、不做自然语言负反馈解析（弱信号误报率高，留待显式 thumbs-down 通道）。

### E2 反思技能（核心 prompt 要点）

- 输入只给 DefectReport 聚合文本（预算受限，走 PromptContribution 正常通道，DegradeRank 中等）。
- 强制三选一输出：`new-skill` / `revise-skill` / `no-action`（no-action 必须给出归类：环境问题 / 一次性失误 / 超出能力边界）。
- 生成 MRE 的规则：最小文件集 + 一条可执行验证命令；验证命令必须是项目 verifyCommands 风格（可本地跑、有明确退出码）。
- 幂等防护：对同一 DefectReport 指纹（工具簇+错误签名）已有候选/已拒绝记录时跳过，防反思循环空转。

### E3 实验区执行流

1. 建 `labs/<turnId>/`，写入 MRE 文件集（或复制最小复现文件）。
2. 以实验 workspace 运行验证链（BuildVerifier 原样复用，10 分钟预算已有）。
3. `revise-skill` 类实验的验证 = 将修订后 prompt 注入一次模拟 turn（新技能触发词命中 MRE 用户消息）+ 验证链通过。
4. TurnScope 在实验 turn 结束时兜底回滚任何越界写入。
5. 通过 → 候选目录落盘；失败 → 实验产物保留供下轮反思，journal 记 `EvolutionExperimentEvent(Success=false)`。

### E4 审批（桌面端）

- `evolution.pending-list` / `evolution.decide` 两个 RPC，对齐 config.save/agent.undo 的既有 RPC 模式。
- 候选卡 UI 复用撤销横幅模式：非阻塞、常驻、点击展开 diff。
- 采纳动作 = 目录移动（candidates → skills），SkillManager 下轮扫描热加载，零重启。

## 四、分阶段实施

| 阶段 | 内容 | 依赖 | 规模预估 |
|---|---|---|---|
| **P1 信号层** | DefectAggregator（E1 三条规则）+ `evolution.inspect` RPC + 单测 | journal 表（已有） | 小 |
| **P2 反思闭环** | 反思技能 + labs 实验区 + 候选目录落盘（E2+E3） | P1 | 中 |
| **P3 审批闭环** | 两个 RPC + 桌面候选卡 + EvolutionDecisionEvent（E4） | P2 | 中 |
| **P4 显式负反馈** | 桌面端 thumbs-down → 结构化负反馈事件 → 进 E1 信号 | P1 | 小 |

每阶段独立可交付、可单独回退（P1 纯只读，零风险起步）。

## 五、不做清单（裁决）

1. ⛔ **Docker/容器沙箱**——依赖假设不成立；实验对象为数据文件，四层轻量沙箱已覆盖风险面。
2. ⛔ **LLM 自改 C# 代码 / 核心 prompt**——自改范围钉死在技能层（数据态资产），代码层进化走人类开发流程。
3. ⛔ **流式实时监控层**——journal 批处理查询已覆盖全部信号，避免为"实时"引入常驻订阅者。
4. ⛔ **自动合并 / CI-CD 管线**——单机应用，本地验证链 + 人工确认即门禁。
5. ⛔ **LLM 置信度信号**——API 不提供，改用行为代理信号（失败簇/修复挣扎/Gap）。
6. ⛔ **新编排框架**——与 Workflow Graph 裁决一致：反思循环就是一次普通 turn + 一个技能，不引入 Graph Engine。

## 六、风险与边界

- **反思循环自喂养**：实验失败也产生事件，可能让反思 turn 无限追踪自身 → E2 幂等指纹防护 + 反思 turn 的事件打上 `origin=evolution` 标记，E1 聚合时排除反思 turn 自身产生的事件。
- **成本**：反思 turn 是额外 LLM 调用 → 默认 cron 每日一次 + 手动触发，频次进配置。
- **误报技能污染**：候选态与正式态物理隔离（目录分离），丢弃零成本；采纳后技能仍受 manifest v2 权限边界约束，最坏情况是提示词质量退化而非系统破坏。
- **与 prompt 预算的相互作用**：新技能默认 `always-listed: false` + 触发词门控，不挤占 24k 系统提示预算。
